# Маркеры доработок и именование метаданных

**Когда читать:** при правке кода типовой конфигурации, при создании объектов
метаданных, реквизитов, ролей, элементов форм.

Часть правил здесь **не может быть задана нейтральным комплектом**: префикс
объектов, название компании в синонимах, формат маркера доработки зависят от
конфигурации и от договорённостей команды. Комплект задаёт механизм; значения
проект задаёт в `docs/rules/project/change-markers.md`. Пока значения не заданы,
действуют правила по умолчанию, описанные ниже.

## Правка типового кода

### Удаляемый типовой код комментируется, а не удаляется

```bsl
НовоеЗначение = ПреобразоватьЗначение(Значение1);
// ТиповаяПроцедура(Значение1, Значение2);
ТиповаяПроцедура(НовоеЗначение, Значение2);
```

Закомментированная строка нужна не как история — историю хранит Git — а как
опорная точка при обновлении типовой конфигурации: по ней видно, от чего именно
отклонились и совпадает ли новая типовая версия с той, которую заменяли.

### Маркеры доработки

Обрамляющие комментарии-маркеры (`// +++ ...` / `// --- ...`) применяются **только
если проект задал их формат** в `docs/rules/project/change-markers.md`. Без
заданного формата маркеры не ставятся вовсе: маркер, который каждый ставит
по-своему, не даёт ни поиска, ни сверки, а diff зашумляет.

Когда формат задан:

- открывающий и закрывающий комментарии — строго в заданном виде;
- после `//` — обязательный пробел;
- в новой процедуре типового модуля маркер ставится **внутри** процедуры, после
  заголовка, а не вокруг неё.

### Полностью новые объекты

В модулях новых объектов маркеры на каждый метод не нужны. Вместо них — один блок
в шапке модуля с описанием объекта.

## Приоритет способа доработки

1. **Подписка на событие** — предпочтительно.
2. **Расширение** — [extensions.md](extensions.md).
3. **Правка типового кода** — последнее средство.

Порядок не про вкус: правка типового кода превращает каждое обновление
поставщика в ручное слияние, и цена платится не тем, кто правил.

## Именование метаданных

Обозначим `<Префикс>` — префикс проекта, заданный в
`docs/rules/project/change-markers.md`. Если проект префикс не задал, `<Префикс>`
раскрывается в пустую строку и все правила ниже остаются в силе без него.

| Элемент | Правило |
|---|---|
| Новые объекты метаданных | имя с `<Префикс>` |
| Синонимы объектов | без префикса; при конфликте — уточнение в скобках |
| Новые роли | имя с `<Префикс>` |
| Подсистемы для новых и изменённых объектов | `<Префикс>ДобавленныеОбъекты`, `<Префикс>ИзмененныеОбъекты` |
| Реквизиты типовых объектов | имя с `<Префикс>` |
| Элементы на типовых формах | имя с `<Префикс>` |

**Внутри новых объектов** — реквизиты, табличные части, элементы форм, команды,
процедуры — **без префикса**: имя объекта уже несёт его, а повторный префикс на
каждом реквизите только удлиняет обращения.

Типовые роли не изменять. Нужные права — новой ролью с префиксом. Изменённая
типовая роль восстанавливается при обновлении поставщика молча, и потеря прав
обнаруживается пользователем.

## Выбор типа объекта метаданных

| Задача | Тип |
|---|---|
| Справочные данные | `Справочник` |
| Хозяйственная операция, событие | `Документ` |
| Накопление количеств и сумм, остатки | `РегистрНакопления` |
| Произвольные данные с измерениями | `РегистрСведений` |
| Отчёт для пользователя | `Отчет` на СКД |
| Обработка данных | `Обработка` |
| Фиксированный набор значений | `Перечисление` |

Разбор выбора между типами регистров — [registers.md](registers.md). Ошибка на
этом шаге исправляется реструктуризацией с потерей данных, а не рефакторингом.
