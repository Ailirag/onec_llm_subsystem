# Тесты: что есть у теста и когда что брать

**Когда читать:** перед тем как писать или править тест любого вида — Web UI,
функциональный, модульный — и перед тем как готовить данные стенда.

Тест проверяет одно утверждение. Всё остальное — подготовить данные, дойти до
нужного состояния, убедиться, что в базе стало то, что должно, — делается самым
прямым из доступных механизмов, а не кликами. Клики медленные и хрупкие: тест,
который двадцать шагов готовит документ через интерфейс, падает на шаге три по
причине, не имеющей отношения к проверке.

## Механизмы

| Задача | Механизм | Где описан |
|---|---|---|
| Подготовить данные под сценарий | исполнитель кода стенда: BSL в `setup`, режим `commit` | ниже; `docs/1c-development-workflow.md`, «Исполнитель кода стенда» |
| Простой CRUD без BSL | стандартный OData стенда | там же, «OData стенда» |
| Проверить, что стало в базе после действия в интерфейсе | исполнитель (запрос) или OData `GET` | ниже |
| Проверить, что видит и может пользователь | Web UI тест | навык `cc-1c-skills:web-test` |
| Проверить логику метода на заданных входах | модульный тест YAxUnit | `docs/rules/unit-tests.md` |
| Подменить зависимость (HTTP, соседний модуль, дату) | Мокито — **только** в модульном тесте | `docs/rules/unit-tests.md` |
| Наполнить стенд общими данными для всех тестов | сид проекта (`functionalTests.seedScript`), BSL-файлы через исполнитель | `docs/1c-development-workflow.md` |
| Разобрать, почему тест упал | проба исполнителем в режиме `rollback` | `docs/rules/debugging.md` |

Исполнитель и OData включаются в манифесте (`standExec.enabled`, `standExec.odata`)
и есть только на стендах. Мокито в сеансе веб-клиента не работает: мок живёт в
сеансе модульного теста.

## Web UI тест: данные — напрямую, проверка — в интерфейсе и в базе

В тестах Web UI доступ к стенду даёт `tests/web-ui/_stand.mjs` (ставит комплект):

- `standExec(code, { params, mode })` — выполнить BSL, вернуть значение `Результат`.
  Ссылки приходят объектами `{ _type, _ref, _presentation }`. Ошибка кода —
  исключение с текстом, сообщениями пользователю и стеком;
- `odata(path, { method, body })` — запрос к `standard.odata`, для коллекции —
  массив;
- `standCapabilities()` — что включено на стенде; исключений не бросает. Для
  диагностики и инструментов, а не для пропуска теста — см. «Правила».

```js
import { standExec, odata } from '../_stand.mjs';

export const name = 'Проведение приходной накладной пишет остаток';
export const tags = ['documents'];

export async function setup(ctx) {
  // Своя метка на прогон: тест не зависит от того, что осталось от прошлых.
  const mark = `ui-${Date.now()}`;
  ctx.state = await standExec(`
    Товар = Справочники.Номенклатура.СоздатьЭлемент();
    Товар.Наименование = Параметры.Метка;
    Товар.Записать();
    Результат = Новый Структура("Товар, Метка", Товар.Ссылка, Параметры.Метка);`,
    { params: { Метка: mark } });
}

export default async function(ctx) {
  const { step, assert, navigateLink, clickElement, fillFields } = ctx;
  await step('Провести накладную с товаром', async () => {
    // ... действия в интерфейсе: то, что проверяет этот тест ...
  });
  await step('В регистре появился остаток', async () => {
    const rows = await odata(
      `AccumulationRegister_ОстаткиТоваров/Balance()?$filter=Номенклатура_Key eq guid'${ctx.state.Товар._ref}'`);
    assert.equal(rows.length, 1, 'остаток по товару не записан');
  });
}
```

## Правила

- **Тест готовит себе данные сам.** На данные стенда, созданные не сидом и не этим
  тестом, не рассчитывать: следующий прогон, чужой тест или пересборка стенда их
  изменят. Общие справочники — сидом; данные сценария — в `setup`.
- **Метка прогона в создаваемых данных** (наименование, номер, комментарий):
  повторный прогон на том же стенде не должен находить данные прошлого.
- **Сид повторяемый.** Сначала найти, потом создать: повторная запись с той же
  ссылкой через OData отвечает ошибкой, а сид без проверки плодит дубли.
- **Проверка состояния базы — запросом, а не открытием формы**, если предмет
  теста не сама форма. Форма показывает не всё и медленно.
- **Проверка читает, а не пишет.** Запрос через исполнитель — в режиме `rollback`
  или `none` без записи; OData — `GET`.
- **Недоступный исполнитель — отказ, а не пропуск.** Тест, которому нужен
  исполнитель или OData, требует `standExec.enabled` в проекте. Выключен — тест
  падает в `setup` с причиной (помощник называет её сам: не опубликован, нет прав,
  стенд собран до включения). `export const skip` по недоступности не ставить:
  пропущенная проверка не выполняется никогда, а зелёный прогон выглядит как
  доказательство. Сценарий, который рано включать, — в `pending/`
  (`docs/1c-development-workflow.md`, «Отложенные сценарии»).
- **Регламентные задания на стенде выключены** базовой подготовкой
  (`standBaseline`, `docs/1c-development-workflow.md`): в файловой базе их выполняет
  сеанс веб-клиента теста посреди шагов. Исключение — доставка серверных
  оповещений БСП: её БСП включает при старте каждого сеанса, и тест не должен
  рассчитывать, что она выключена. Результат задания, нужный тесту, тест
  получает вызовом его процедуры исполнителем в `setup`, а не ожиданием расписания.
  Тест нового задания не читает его состояние со стенда: вызывает обработчик
  обновления исполнителем в режиме `rollback` и по результату проверяет
  `Использование` и расписание.
- **Под администратором стенда.** Помощник входит под ним; отдельную роль под
  OData и исполнитель не заводить. Проверка прав пользователя — отдельный Web UI
  тест под этим пользователем, а не OData.
- **Только стенды.** Исполнитель и OData тестов не направлять на рабочие базы.

## Чего не делать

- Не готовить данные кликами, если сценарий проверяет не саму подготовку.
- Не писать в тесте свою обвязку `fetch` с адресом и входом: она уже в
  `_stand.mjs` и расходится с правилами стенда при первой их смене.
- Не мокать в Web UI тесте: Мокито там не работает, а подмена внешнего сервиса
  на стенде — адрес в настройках базы или демонстрационное расширение.
