# Модульные тесты на YAxUnit

**Когда читать:** при написании или правке модульного теста, при настройке
адаптера `unitTests.script`, при выборе, чем проверять логику: модульным тестом,
пробой на стенде или сценарием Web UI.

Движок — [YAxUnit](https://github.com/bia-technologies/yaxunit)
([документация](https://bia-technologies.github.io/yaxunit/)). Комплект его не
поставляет: движок выбирает проект, фаза знает только адаптер
(`docs/1c-development-workflow.md`, раздел «Модульные тесты»). Утверждения ниже
проверены по коду YAxUnit (версии 25.12, коммит `23fd2db`). При переходе на
другую версию перепроверять их по коду, а не по документации: документация в
нескольких местах расходится с кодом (см. «Отчёт»).

## Что чем проверять

Общая таблица механизмов тестирования — `docs/rules/testing.md`; здесь — то, что касается модульных тестов.

| Вопрос | Чем |
|---|---|
| Метод возвращает верное на заданных входах, пишет верные движения | модульный тест YAxUnit |
| Как код поведёт себя на данных стенда — разовая проверка гипотезы | проба исполнителем кода стенда в режиме `rollback` (`docs/rules/debugging.md`) |
| Форма открывается, команда доступна, пользователь проходит сценарий | Web UI тест |
| Наполнить стенд данными под тесты и инструкции | сид через исполнитель кода стенда |

YAxUnit **не наполнитель стенда**. `ЮТест.Данные()` работает только внутри
прогона тестов: без контекста прогона запись падает
(`ЮТОбщий.ПараметрыЗаписи` читает опции движка из контекста). Повторный запуск
плодит дубли — поиска «уже есть» у построителя нет. Данные стенда пишутся сидом.

## Где живут тесты

- Тестовые модули — в отдельном расширении проекта (по умолчанию движок ищет
  тесты в расширении `tests`, фильтр `filter.extensions`). В основную
  конфигурацию и в поставляемые расширения тесты не кладутся.
- Расширение с тестами объявляется в `extensions[]` как необязательное
  (`required: false`) только если оно должно уходить на стенды фаз; в поставку
  тестовое расширение не собирается.

## Адаптер `unitTests.script`

Адаптер получает `-BasePath`, `-ReportPath` и необязательные `-Tests`,
`-Modules`, `-Tags`, запускает тонкий клиент с `/C RunUnitTests=<файл.json>` и
разбирает отчёт. Обязательное:

- **Расширения применены по имени.** Загруженное, но не применённое расширение
  движок не видит: прогон отрабатывает и пишет отчёт с нулём тестов
  (`docs/known-issues.md` комплекта, п. 6). Нулевой отчёт адаптер обязан считать
  отказом, а не успехом.
- **У расширений движка и тестов сняты безопасный режим и защита от опасных
  действий** — требование YAxUnit. Готовая функция комплекта:
  `Disable-WorkflowExtensionSafeMode -RepositoryRoot … -InfoBase … -ExtensionNames YAXUNIT,tests -LogPath …`
  (`scripts/workflow/Workflow.Common.ps1`). Свою COM-обвязку не писать: ловушки
  COM из PowerShell описаны в `docs/known-issues.md` комплекта, п. 13, и закрыты
  этими функциями.
- **Нужна интерактивная сессия Windows**: прогон идёт тонким клиентом. Под
  службой без рабочего стола клиент не стартует.
- **Стартовые окна конфигурации** (обновление, предупреждения БСП) достаются
  первому тесту (`docs/known-issues.md`, п. 5). Снимаются настройкой в сиде.
- Файл конфигурации прогона: `filter` (`extensions`, `modules`, `tests`, `tags`),
  `reportFormat`/`reportPath`, `exitCode` (файл с 0 или 1 — признак успеха
  берётся из него, а не из кода завершения процесса), `closeAfterTests: true`,
  `showReport: false`, `logging.file`.

## Регистрация и изоляция

- Серверный тест, который пишет данные, регистрируется с `ВТранзакции()`: движок
  откатит транзакцию после теста. В транзакцию входят только тест и события
  «перед/после каждого теста»; данные из «перед всеми тестами» остаются.
- Клиентский тест транзакцией не изолируется (настройка игнорируется). Для него —
  `УдалениеТестовыхДанных()`.
- По умолчанию обе настройки выключены: без них тестовые данные остаются в базе.

## Тестовые данные

- `ЮТест.Данные().КонструкторОбъекта(...)`: реквизиты, от которых зависит
  проверяемая логика, задаются **явно** (`Установить`). `Фикция` — только для
  технически обязательных полей, не влияющих на результат:
  - строка заполняется случайными символами на всю длину реквизита, число может
    оказаться отрицательным, составной тип выбирается случайно;
  - ссылочное поле получает НОВЫЙ объект с пустыми владельцем, родителем и
    реквизитами;
  - `ФикцияОбязательныхПолей` видит только `ПроверкаЗаполнения = ВыдаватьОшибку`
    в метаданных, программную `ОбработкаПроверкиЗаполнения` — нет.
- `Записать(, Истина)` пишет с `ОбменДанными.Загрузка` — в обход обработчиков.
  Допустимо, только если обработчик не предмет теста; служебные записи БСП при
  этом не создаются.
- `КонструкторДвижений` пишет движения мимо проведения. Годится для теста
  логики, читающей регистр; тест проведения так не пишется.
- `ЗагрузитьИзМакета` создаёт ссылки из ячеек заново, существующие не ищет.

## Проверки

- Значения — `ЮТест.ОжидаетЧто(...)`.
- Состояние базы — `ЮТЗапросы` (`Записи`, `ЗначенияРеквизитов`,
  `ДвиженияДокумента`) плюс `ОжидаетЧто`. `ОжидаетЧтоТаблицаБазы` проверяет
  наличие записи, но в сообщении об отказе нет фактических данных — разбирать
  такой отказ дольше.
- `ЮТЗапросы` работают с одной таблицей и без `РАЗРЕШЕННЫЕ`: тест запускается
  под полноправным пользователем.

## Мокито

- Подменить можно только метод **конфигурации** (общего модуля, менеджера,
  объекта, набора записей), и только если в тестовом расширении есть перехватчик
  `&Вместо` с `МокитоПерехват.АнализВызова` на этот метод. Перехватчики
  создаются навыками `cfe-borrow` и `cfe-patch-method` и обновляются при смене
  сигнатуры метода.
- Методы платформы (`ТекущаяДатаСеанса`, `Новый HTTPСоединение`), методы
  расширений и внешних обработок не подменяются. Подменяемой делается обёртка —
  метод конфигурации, который зовёт платформу.
- Мок действует в сеансе теста и только на время одного теста. В фоновом
  задании и в другом сеансе — в веб-клиенте, у сценария инструкции — он не
  срабатывает: вызов уходит в оригинал.
- Параметры мок не меняет: доступны вернуть значение, выбросить исключение,
  пропустить вызов, наблюдать.

## Отчёт

- Форматы: `jUnit`, `allure` и полный дамп `dumpjson` (в документации назван
  `JSON` — такого имени движок не знает).
- Сообщения `ЮТест.ДобавитьСообщение` попадают в отчёт только у упавших и
  пропущенных тестов.

## Чего не делать

- Не использовать внутренний канал `rpc` YAxUnit (запуск без перезапуска для
  1С:EDT): протокол не документирован и не обещан внешним клиентам. Для быстрых
  итераций есть исполнитель кода стенда.
- Не наполнять стенд тестами YAxUnit — см. «Что чем проверять».
- Не считать зелёным прогон с нулём выполненных тестов.
