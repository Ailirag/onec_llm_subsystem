# Обзор подсистемы LLM для 1С

Документ описывает текущее состояние решения: его назначение, архитектуру,
пользовательские сценарии, модель безопасности и известные ограничения.

Ограничения ниже фиксируют существующую реализацию, а не неизменные требования.
Они могут быть пересмотрены при дальнейшем развитии подсистемы.

## Назначение

Подсистема LLM предназначена для управляемого подключения языковых моделей к
прикладным конфигурациям 1С:Предприятия. Она объединяет обычный диалог с
моделью, агентский анализ данных, работу с вложениями, RAG и внешними
MCP-инструментами.

Основные цели решения:

- предоставить единый интерфейс для разных LLM-провайдеров;
- разрешить модели исследовать метаданные и данные базы только в заданных
  администратором границах;
- отделить настройки провайдеров, моделей, агентов и прав доступа от
  прикладной логики конкретной конфигурации;
- сохранять историю диалогов и технический аудит операций;
- учитывать расход токенов и ограничения провайдеров;
- позволить устанавливать решение как расширение или встраивать его объекты в
  основную конфигурацию.

## Варианты поставки

Решение поддерживает два способа внедрения:

- `cfe llm` содержит канонические XML-исходники расширения;
- `cf llm` формируется как конфигурация-донор для сравнения и объединения;
- собранный `LLM_isolated*.cfe` предназначен для установки расширения;
- собранный `LLM_Subsystem.cf` предназначен для встраивания объектов в
  основную конфигурацию.

Изолированное расширение не должно ссылаться на прикладные объекты конкретной
конфигурации. Связи с такими объектами, прежде всего источники RAG, добавляются
сознательно в проекте внедрения.

Все объекты решения включены в подсистему `LLM`, ее дочерние подсистемы или в
явно задокументированный список технических исключений. Состав проверяется
автоматизированным скриптом перед сборкой конфигурации-донора.

## Провайдеры и модели

Поддерживаются следующие типы провайдеров:

- OpenAI;
- Yandex AI;
- Z.AI;
- произвольный OpenAI-совместимый API;
- Ollama;
- LM Studio.

Поддержаны протоколы `Chat Completions` и `Responses API`. Для провайдера можно
настроить API-ключ, адреса сервисов, таймаут, максимальное количество потоков,
лимит запросов в минуту и суточный лимит токенов.

Подсистема умеет получать перечень моделей у поддерживающего это API
провайдера. Пользователь выбирает необходимые модели в отдельной форме, после
чего они создаются или обновляются в справочнике моделей.

Для модели хранятся идентификатор API, описание, контекстное окно, цена,
Folder ID и заявленные возможности. Отдельно учитываются поддержка изображений,
файлов и структурированных ответов. Для Z.AI предусмотрен каталог GLM-моделей
с описанием их назначения.

Стандартные провайдеры создаются процедурой инициализации. Решение не зависит
от предопределенных элементов расширения, использование которых ограничено в
режиме совместимости 1С 8.3.17.

## Агенты

Агент является настраиваемой конфигурацией поведения модели. Он может включать:

- системную инструкцию;
- температуру и максимальное количество токенов;
- агентский режим;
- дополнительный контекст;
- веб-поиск и перечень разрешенных ресурсов;
- профиль доступа к данным;
- профиль MCP;
- RAG-коллекции, веса, лимиты и фильтры разрешений;
- правила доступности пользователям.

Без выбранного агента выполняется обычный диалог с моделью. В агентском режиме
модель получает описания доступных инструментов и может выполнять
многошаговый цикл: исследовать структуру базы, формировать запрос, проверять
его, получать данные и готовить итоговый ответ.

Многошаговый цикл поддерживается для OpenAI-совместимого Chat Completions и
Responses API. Для Responses API продолжение контекста выполняется через
`previous_response_id` и `function_call_output`.

## Исследование метаданных и данных

Встроенный агентский контур предоставляет инструменты:

- `metadata_search` для поиска доступных объектов метаданных;
- `metadata_describe` для получения разрешенных полей и табличных частей;
- `query_validate` для проверки запроса 1С без выполнения;
- `query_execute` для выполнения проверенного запроса;
- `catalog_record_counts` для безопасного массового подсчета элементов
  разрешенных справочников;
- разрешенные инструменты подключенных MCP-серверов.

Запросы выполняются без привилегированного режима. Доступ одновременно
ограничивается ролями и RLS текущего пользователя, профилем агента, белым
списком объектов и перечнем запрещенных полей.

Поддерживается только чтение данных. Обычная выборка должна содержать в
верхнем `ВЫБРАТЬ` буквальное ограничение `ПЕРВЫЕ N`. Без него допускаются
только ограниченные однострочные агрегаты без группировки, итогов и
объединений. Пакетные запросы, временные таблицы, комментарии и конструкции
изменения данных запрещены.

Параметры запроса передаются типизированным массивом. Поддерживаются строки,
числа, булевы значения и даты. Для выбранных объектов профиль может требовать
обязательного ограничения периодом.

Администратор задает максимальное количество шагов, запросов к данным, строк
результата и длину текста запроса. Эти значения являются настройками профиля,
а не жесткими пределами платформы.

## Доступ пользователей

Для агента предусмотрены режимы доступа:

- всем пользователям подсистемы LLM;
- только по назначениям;
- отключен.

Персональное назначение использует уникальный идентификатор пользователя
информационной базы. Также поддерживаются собственные группы пользователей.
Назначение может переопределять профиль доступа агента для конкретного
пользователя или группы.

Для групп используется приоритет. Если назначения одинакового приоритета дают
разные профили данных, доступ блокируется до устранения противоречия.

Подсистема содержит отдельные роли для обычного пользователя LLM, анализа
данных агентом, консоли запросов, администрирования MCP и полного доступа.
Роль агентского анализа разрешает механизм инструментов, но сама по себе не
дает право чтения прикладных данных.

## Диалоги

Диалог с агентом реализован в управляемой форме с HTML-лентой сообщений.
Интерфейс отображает сообщения пользователя и модели, Markdown-разметку,
статус операции, длительность, статистику токенов и ход выполнения
инструментов. Панель шагов агента позволяет просматривать их аргументы и
результаты.

Запрос запускается фоновым заданием. Форма периодически получает состояние
операции и позволяет запросить отмену на безопасной точке выполнения. Это
предотвращает блокировку интерфейса на все время обращения к модели.

История бесед сохраняется в информационной базе. Пользователь может создавать,
искать, открывать, переименовывать и архивировать свои диалоги. Вместе с
диалогом сохраняются провайдер, модель, тип API, агент, системная инструкция,
глубина истории и идентификатор продолжения Responses API. Для беседы,
открытой из прикладного объекта, также сохраняются сценарий, версия и JSON
контекста, тип, ключ и представление источника.

Доступ к диалогу проверяется по уникальному идентификатору текущего
пользователя. Штатные методы подсистемы не позволяют открыть или изменить
диалог другого пользователя.

## Интерфейсная интеграция

Администратор может зарегистрировать доступные действия в справочнике мест
запуска сценариев — вручную или мастером «Новое AI-действие», который по
ответам заводит карту извлечения, сценарий и место одной транзакцией. Место
связывает сценарий с типом интерфейсного контекста и полным именем метаданных.
Универсальная форма показывает только активные сценарии, доступные текущему
пользователю, и открывает обычный асинхронный диалог с уже заполненными
агентом, моделью, контекстом и начальным запросом.

Что модель получает, настраивается в месте: файл объекта, данные самого
объекта — реквизиты и строки табличных частей текстом с номерами строк — или
только то, что расскажет пользователь. Действие может начинаться разговором:
пользователь словами объясняет, что нужно, модель уточняет недостающее, а
результат по карте формируется по его кнопке. Результат показывается,
переносится в форму, записывается в объект, обновляет существующие строки по
номеру или создает новый объект — например шаблон согласования, собранный в
разговоре из помощника раздела LLM. Для перечислений и отмеченных справочников
модель выбирает значение из перечня существующих, а не пишет как в документе.

Кому видно действие, сужается ролью конфигурации или группой доступа БСП —
внутри круга пользователей агента. В ход действия вмешивается код — процедуры
конфигурации и методы внешней обработки на этапах: проверка при выборе
действия, перед шагом и перед действием, подготовка запроса (подать модели
свой файл, дописать данные), ответ модели до показа человеку и после действия.
Значения, которые ядро найти не умеет, — полные роли и автоподстановки
Документооборота — перечисляет и находит адаптер конфигурации, внешняя
обработка, заданная одной настройкой. Готовое действие переносится между базами
пакетом, а описать его можно и самому, JSON-файлом по схеме
`docs/scenario-package.schema.json`: недостающее загрузка выведет из
метаданных, сценарий создаст по образцу.

Для конфигураций на БСП поставляются исходники дополнительной внешней
обработки вида `ЗаполнениеОбъекта`. Она получает выбранные ссылки из БСП и
передает их универсальному ядру. Команда без прикладного объекта доступна в
подсистеме как запасная точка входа.

Конфигурационно-зависимая семантика, например получение конкретной версии
файла договора из строки вложений Документооборота, остается в небольшом
адаптере внедрения. Такой адаптер только извлекает ссылки и вызывает публичный
клиентский метод — при необходимости сразу на нужном действии; правила
сценариев и доступа не дублируются.

Подробности: [Универсальная интерфейсная интеграция](universal-ui-integration.md).

## Вложения

К сообщению можно прикреплять:

- PNG, JPEG и WebP;
- PDF;
- DOC, DOCX, XLS, XLSX, PPT, PPTX, RTF и ODT;
- TXT, LOG, Markdown, JSON, XML, HTML, CSV и TSV;
- BSL, OS, Python, JavaScript, TypeScript, SQL и YAML.

Для провайдера можно назначить отдельную мультимодальную модель анализа
вложений. Она предварительно извлекает содержимое и формирует структурированный
результат, который затем передается основной модели диалога.

Конвейер вложений один на всю подсистему: и обычный диалог, и сценарий из
интерфейса передают файл одинаково — вложением агентской операции. Отдельного
«разбора файлов средствами конфигурации» нет.

### Чем читать вложение

Способ разбора — настройка, а не свойство кода. Реквизит
`СпособРазбораВложений` есть у провайдера и у сценария; сценарий важнее,
пустое значение у обоих означает «Авто».

Для каждого вложения ядро выбирает маршрут:

| Маршрут | Что происходит | Какая модель нужна |
|---------|----------------|--------------------|
| Текст | Текст файла читает 1С. Короткий уходит основной модели целиком, длинный пересказывает анализатор. | любая |
| Файл | Файл загружается в Files API и передается модели как `input_file`. | у Yandex — любая, у остальных — с вводом файлов |
| Картинка | Изображение уходит модели изображением. | со зрением |
| OCR | Yandex Vision распознает PDF, JPEG или PNG; модели уходит текст с координатами блоков. | любая |

| Способ | Маршруты |
|--------|----------|
| `Авто` | У Yandex все, кроме текста, — «Файл». У остальных провайдеров картинки — «Картинка», документы — «Файл». |
| `Мультимодально` | Картинки — «Картинка», документы — «Файл». Нужен, когда важно само изображение: фотография, схема, график. |
| `OCR` | PDF, JPEG и PNG — «OCR», остальное — обычным путем. Нужен, когда важны координаты блоков: таблицы, бланки, многоколоночный текст. Требует роли на Vision. |

Текстовый файл при любом способе читается средствами 1С: распознавать в нем
нечего. Если его разбор помещается в контекст вложения (12 тысяч символов),
основная модель получает текст целиком, без анализатора, — почему, см. ниже.

### Вложения у Yandex: что происходит на самом деле

Проверено прямыми запросами к API и затем через ядро в Документообороте.

**Yandex сам извлекает содержимое файла, переданного по `file_id`.** Текстовый
слой PDF, OCR скана без текстового слоя, OCR картинок PNG и JPEG, DOCX, XLSX,
PPTX, RTF, ODT, TXT — модели уходит уже текст. Поэтому такой файл читает любая
модель Yandex, мультимодальная не нужна: проверено на `qwen3.6-35b-a3b`,
текстовых `deepseek-v4-flash` и `gpt-oss-20b` и на YandexGPT 5 Lite и Pro.
Страница стоит около 500 входящих токенов — против ~2200 у той же страницы,
переданной картинкой. Роли на Vision этому распознаванию не нужно.

Отсюда «Авто» у Yandex: все, кроме текста, — через Files API. Модель анализа
вложений для этого маршрута не обязательна: если она назначена у провайдера,
разбирает она, иначе — основная модель операции. Ядро не требует от нее
способностей к изображениям и файлам и не заводит ее само.

Ограничения, найденные по пути:

- **Файл — только по `file_id`.** Встроить его в запрос нельзя: на `file_data`
  API отвечает `Only files with file_id are supported in input`, а `image_url`
  с `data:application/pdf` отклоняется. `input_file` есть только в Responses
  API — Chat Completions его не принимает, поэтому разбор вложений всегда идет
  через Responses, какой бы API ни был у основной модели.
- **Тип файла нужно передавать явно.** Без `Content-Type` у части multipart
  Yandex считает файл `application/octet-stream` и отклоняет его с 400
  `Mime type ... is not supported`; PDF он узнает сам, PNG и Office — нет.
- **Файл и вопрос — разными сообщениями.** YandexGPT из сообщения с несколькими
  частями берет только первую: при «файл, вопрос» теряет вопрос и переспрашивает
  «что сделать с текстом», при «вопрос, файл» теряет файл. Раздельные сообщения
  одинаково читают все проверенные модели.
- **WebP Yandex не извлекает**: загрузка проходит, а до модели ничего не
  доходит. Платформа WebP тоже не декодирует, поэтому перевести его в PNG
  средствами 1С нельзя — ядро сразу отказывает и просит PNG или JPEG.
- **Качество зависит от модели.** YandexGPT 5 Lite получает файл, но разбирает
  его скупо: на просьбу «извлеки реквизиты договора» вернула только стороны,
  их ИНН и КПП — слово «реквизиты» поняла как раздел договора. Qwen и DeepSeek
  на том же файле и вопросе дают все значения. По скорости наоборот: Lite
  отвечает за 12–13 с, Qwen за 25–35 с, DeepSeek за 45–55 с — у последних
  разбор в несколько тысяч токенов.

### Проверка доставки файла

Файл, который доставляет модели провайдер — через Files API или картинкой, —
может до нее не дойти молча: ответ 200, модель отвечает, а вложения в запросе
нет. На Yandex это наблюдалось на одном и том же PDF и одном и том же коде: то
«файл не предоставлен», то полный разбор. Так же ведет себя поврежденный PDF —
загрузка проходит, извлечь из него нечего, модель получает только вопрос.

Без проверки такой отказ выглядит успехом: разбор «готов», поля пустые, а
пустые значения правильного типа засчитываются как распознанные.

Поэтому ядро считает попытку неудачной, если:

- в ответе анализатора `file_received` равно `false`;
- поле есть, но `summary` и `extracted_text` пусты — маленькие модели на
  поврежденном файле отвечают `file_received: true` с пустыми полями, и одному
  флагу верить нельзя;
- модель не вернула текст вовсе.

Неудачная попытка повторяется с новой загрузкой, до трех раз; каждая пишется в
журнал регистрации под событием `AI.Вложения.ФайлНеДоставлен`, после третьей
ядро отказывает с объяснением. Текст и результат OCR подставляются в запрос
самой подсистемой — проверять их доставку не нужно, но пустой ответ
повторяется и для них, см. ниже.

Признак `file_received` сформулирован через содержимое, а не через зрение:
`false` — только если в сообщении нет ничего, кроме имени файла. На вопрос
«видишь ли ты файл» текстовая модель, получившая от провайдера распознанный
текст картинки, честно отвечает «нет», и проверка отвергала бы исправно
доставленный файл. Ответ без поля и не-JSON считается полученным, чтобы модели,
которые пишут прозой, не уходили в повторы.

### Что анализатор оставляет от файла

Анализатор возвращает не файл, а разбор: `summary`, `extracted_text`,
`entities` и так далее. Инструкция велит ему извлечь только факты, относящиеся
к вопросу, а вопрос — промт сценария. Какие поля потом из разбора будут
извлекать, он из промта не знает и решает сам. На договоре с разделом «Особые
условия» `deepseek-v4-flash` в 5 из 8 одинаковых запросов этот раздел
выбрасывал, и тип договора, зачет и перепродажа приходили пустыми. Лимит ответа
тут ни при чем: ответы заканчивались штатно, не дойдя и до трети лимита.

Поэтому:

- **короткий текст не пересказывается.** Его разбор 1С собирает сама:
  `extracted_text` — весь текст, `summary` — пометка, что файл передан целиком.
  Модель анализа не вызывается, и это еще полминуты экономии;
- **анализатору перечисляются поля схемы ответа.** Если у операции есть схема,
  в вопрос попадает список ее полей с описаниями и просьба перенести все
  фрагменты, из которых они следуют, в `extracted_text`. На том же договоре
  раздел сохранился во всех 8 запросах (с лимитом из следующего пункта);
- **у анализатора запас лимита.** Рассуждающие модели тратят лимит ответа и на
  скрытые рассуждения. С перечнем полей `deepseek-v4-flash` рассуждает дольше —
  до 6–8 тысяч токенов при видимом ответе около тысячи, — и прежний лимит в
  8000 изредка обрывал ответ пустым. Лимит анализатора — 16000: в 8 запросах
  подряд ответ не превысил 6,5 тысячи. Параметр `reasoning_effort` Yandex
  принимает, но рассуждения он не сокращает;
- **пустой ответ повторяется на любом маршруте**, до трех раз, с событием
  `AI.Вложения.ПустойРазбор` в журнале регистрации. Если модель израсходовала
  лимит на рассуждения, ошибка говорит именно это.

Для вложения сохраняются файл, MIME-тип, размер, хеш, статус, результат
анализа, использованная модель, ошибка и отдельная статистика токенов. У
короткого текста модели нет: он не анализировался.
Устаревшие двоичные данные могут очищаться регламентным обслуживанием.

## MCP

Поддерживаются удаленные MCP-серверы с HTTP-транспортом и JSON-RPC. Подсистема
может проверить подключение, получить список инструментов, сохранить их схемы
и отметить несовместимые определения.

В профиль MCP включается явный список разрешенных инструментов. Для профиля
задаются максимальное количество вызовов, общий таймаут и максимальный размер
результата. Поддерживается отсутствие авторизации, Bearer, Basic и
произвольный HTTP-заголовок. Секреты MCP хранятся отдельно от описания сервера.

Модели передаются только активные, совместимые инструменты с режимом
автоматического выполнения. Внешний MCP-инструмент выполняется вне границ
информационной базы и может обладать собственными полномочиями.

## RAG

RAG-контур использует OpenAI-совместимый Embeddings API и Qdrant. В него входят:

- очередь подготовки данных;
- очередь векторизации;
- пакетное получение векторов и загрузка в Qdrant;
- UUID и хеши чанков для идемпотентной обработки;
- обновление изменившихся чанков и удаление устаревших точек;
- проверка доступности embedding-сервиса и Qdrant;
- фильтры по организации, тенанту, праву и типу данных.

Агенту можно назначить несколько коллекций с весами, лимитами фрагментов и
минимальным порогом сходства.

Правила преобразования конкретных прикладных объектов в текст и подписки на
их изменение не создаются автоматически. Они реализуются сознательно в
проекте внедрения, чтобы расширение не зависело от состава целевой базы.

## Эксплуатация и аудит

Регламентные задания обрабатывают очередь запросов, подготовку RAG,
векторизацию и очистку журналов и диалогов. Константами настраиваются
параллелизм, повторные попытки, сроки хранения и общий таймаут запроса к
модели. Провайдер может переопределить общий таймаут. Все константы собраны в
одной форме: раздел LLM → «Сервис» → «Настройки подсистемы LLM»; отдельных
команд у констант в меню нет.

В журнале запросов сохраняются провайдер, модель, результат, длительность,
входящие, исходящие и инструментальные токены. Токены анализа вложений
учитываются отдельно. Инструментальные токены являются детализацией входящих
и не прибавляются повторно к общему расходу.

Шаги агентской операции хранятся отдельно. Технический аудит инструмента
записывается в журнал регистрации с событием `AI.Агент.Инструмент`; аргументы
и строки результата в событие не включаются.

## Совместимость

Текущий режим совместимости расширения: 1С:Предприятие 8.3.17. Поддерживается
управляемое приложение, файловый и клиент-серверный варианты работы.

Для обращения к внешним API сервер 1С должен иметь сетевой доступ к ним.
Совместимость с конкретной конфигурацией зависит от ее режима совместимости,
ролей, RLS, переопределений и ограничений расширений. Установку необходимо
проверять на копии целевой информационной базы.

## Безопасность

Внутренние инструменты анализа данных не выполняют запись в прикладные объекты.
Доступ строится по принципу пересечения прав пользователя и профиля агента.
Это не отменяет необходимость минимально достаточных ролей в основной
конфигурации.

Выбранные данные, вложения и результаты запросов могут передаваться внешнему
провайдеру модели. При внедрении необходимо учитывать персональные данные,
коммерческую тайну, требования к размещению данных и трансграничной передаче.

API-ключи и MCP-секреты хранятся средствами 1С. Их нельзя включать в Git,
тестовые выгрузки или публичные журналы.

## Текущие ограничения

Следующие ограничения описывают текущую реализацию и могут быть пересмотрены:

- модель может сформировать синтаксически неверный запрос 1С; валидатор не
  допустит его выполнение, но попытка потратит шаг агентского цикла;
- внутренние инструменты предназначены только для чтения данных;
- асинхронный интерфейс использует фоновое задание и периодический опрос, а не
  потоковую выдачу токенов;
- MCP поддерживается только по HTTP, без локального `stdio`-транспорта;
- режим интерактивного подтверждения отдельного MCP-вызова пока не образует
  законченного пользовательского сценария;
- локальное реле персональных авторизаций Claude или Codex не входит в
  решение;
- изоляция истории диалогов реализована прикладными проверками, без RLS на
  собственных регистрах подсистемы;
- встроенной интеграции с корпоративным Vault или KMS нет;
- поддержка конкретного формата вложения зависит от возможностей выбранного
  провайдера и мультимодальной модели;
- запись и создание объекта по результату модели минуют форму объекта: то, что
  конфигурация делает только в форме (в Документообороте — отметку о проверке
  шаблона процесса), выполняется, когда человек откроет и запишет карточку;
  правила предметной области, которых модель знать не может, задаются
  подсказками полей карты;
- RAG требует отдельно развернутых и доступных серверу 1С сервисов Embeddings
  и Qdrant;
- наполнение RAG данными конкретной конфигурации требует проектной интеграции;
- получение моделей и отдельные функции API зависят от фактической
  совместимости провайдера с заявленным протоколом;
- режим совместимости 8.3.17 не гарантирует автоматическую совместимость с
  каждой прикладной конфигурацией;
- встроенные проверки и дымовые сценарии снижают риск регрессий, но не
  заменяют приемочные, нагрузочные и информационно-безопасностные испытания.

Возможными направлениями развития являются потоковый вывод, дополнительные
транспорты MCP, внешнее хранилище секретов, RLS для данных подсистемы, более
строгий синтаксический помощник запросов и типовые адаптеры наполнения RAG.
