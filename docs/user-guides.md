# Инструкции для пользователей

Этап сборки, который получает пошаговую инструкцию не из текста, а из живой
базы: прокликивает сценарий в веб-клиенте, снимает каждый шаг, дорисовывает
поверх страницы стрелку и курсор мыши и собирает один HTML-файл.

Смысл в том, что инструкция не расходится с системой. Переименовали команду,
переставили кнопку, добавили уточнение — пересобрали, и на снимках новое
расположение, а не то, каким оно было на момент написания текста.

## Запуск

```powershell
.\tools\Build-UserGuide.ps1 -Url http://localhost:8081/do21 -Scenario contract-fill
.\tools\Build-UserGuide.ps1 -Scenario batch-queue -Parameters @{ 'документы' = @('ПСТ-2026/417', 'ПСТ-2026/418') }
```

| Параметр         | По умолчанию                 | Назначение                        |
|------------------|------------------------------|-----------------------------------|
| `-Url`           | `http://localhost:8081/do21` | Публикация базы, по которой кликаем |
| `-Scenario`      | `contract-fill`              | Имя файла в `tests\ui\guides`      |
| `-Parameters`    | умолчания сценария           | Имена, которые зависят от базы: список, документы, действие |
| `-ApplyResults`  | нет                          | Выполнять шаги, которые записывают данные в базу |
| `-OutputRoot`    | `build\guides`               | Куда складывать результат          |
| `-WebTestRunner` | ищется сам                   | Путь к `run.mjs` из `cc-1c-skills` |

Результат — `build\guides\<сценарий>\index.html` и снимки шагов рядом. Файл
самодостаточный: стили внутри, картинки вставлены как `data:`-URI, внешних
ссылок нет. Его можно переслать почтой или выложить на портал как есть.

Этап **не входит в обычный прогон тестов** и запускается руками: он ходит в
базу, обращается к модели (это деньги и минуты) и зависит от данных, которые в
базе есть. Прогон `contract-fill` по ДО21 занимает около полутора минут.

### Имена из базы

Сценарий кликает по тексту: по строке документа в списке и по подписи действия
в помощнике. Эти имена задает база, поэтому сценарий берет их из параметров, а
умолчания у него — стенда Документооборота. Ключи перечислены в начале каждого
сценария:

| Сценарий        | Ключ        | По умолчанию |
|-----------------|-------------|--------------|
| `contract-fill` | `список`    | `Справочник.ВнутренниеДокументы` |
|                 | `документ`  | `ПСТ-2026/417` — текст из строки договора |
|                 | `действие`  | `Извлечь реквизиты из файла` |
| `batch-queue`   | `список`    | `Справочник.ВнутренниеДокументы` |
|                 | `документы` | `ПСТ-2026/417`, `23.09.2026` — по тексту из строки каждого договора |
|                 | `действие`  | `Разобрать пачку договоров` |

Действия нет в помощнике — ошибка перечисляет те, что есть. Строки документа
нет в списке — ошибка говорит, какую не нашли.

### Запись в базу

По умолчанию сборка **ничего не записывает**. Шаг, который записывает данные, —
«Записать в объект», «Создать …», свое действие, «Записать объект» — снимается с
указателем на кнопку, но кнопка не нажимается, а комментарий шага говорит об
этом. «Заполнить форму» нажимается всегда: она только переносит значения в
форму, а записывает ее человек, и после сборки форма закрывается без записи.

`-ApplyResults` выполняет и шаги записи — только на тестовом стенде: иначе
сборка инструкции поменяет документы базы.

## Как устроено

Сценарий исполняет тот же раннер веб-тестов из `cc-1c-skills`, что и UI-смоук.
Поиск элемента по тексту, подсветка, ожидание перерисовки, работа с формами и
таблицами уже решены там — здесь они не дублируются.

Скрипт `Build-UserGuide.ps1` проверяет публикацию, подставляет в сценарий две
константы — каталог вывода `ВЫХОД` и `ПАРАМЕТРЫ`: значения `-Parameters` и флаг
`записывать` (контекст раннера не дает сценарию ни аргументов, ни переменных
окружения) — и запускает `run.mjs`.

Раннер ищется в кэше плагинов и Codex, и Claude Code
(`%USERPROFILE%\.codex\plugins\cache\cc-1c-skills\…` и
`%USERPROFILE%\.claude\plugins\cache\cc-1c-skills\…`), берется самая свежая
установка — так же, как для UI-смоука (`tools\WebTestRunner.ps1`). При первом
запуске скрипт ставит зависимости раннера (`npm ci`) в каталог плагина: другого
места раннер не видит.

Сценарий исполняется как тело `async`-функции: импортов нет, функции раннера
доступны глобально. Доступны в том числе `navigateLink`, `clickElement`,
`fillFields`, `getFormState`, `highlight`, `unhighlight`, `screenshot`, `wait`,
`getPage`, `writeFileSync`.

## Свой сценарий

Новая инструкция — это новый файл `tests\ui\guides\<имя>.mjs`; скрипт сборки
менять не нужно, имя передается параметром `-Scenario`.

Образец — [`tests/ui/guides/contract-fill.mjs`](../tests/ui/guides/contract-fill.mjs).
В нем вся механика вынесена в одну функцию `снимок(подпись, цель, комментарий)`:
она подсвечивает элемент, рисует указатель, снимает экран и копит шаги, а сам
сценарий читается как последовательность действий пользователя.

Практика, которая себя оправдала:

- **комментарий к шагу объясняет «почему», а не повторяет «что»**. Подпись и так
  видна на снимке; ценность в том, чего на снимке нет: что список показывает
  только настроенные действия, что интерфейс в этот момент не заблокирован,
  что решение о записи остается за человеком;
- **необязательные шаги оборачиваются в try/catch**. Всплывающие подсказки
  конфигурации появляются не всегда, и инструкция не должна из-за них падать;
- **ожидание модели — это цикл по `getFormState()`**, а не фиксированная пауза:
  модель отвечает по-разному, а инструкция должна собираться одинаково;
- **имена из базы — через `параметр(имя, поУмолчанию)`**, а не строкой в коде:
  действия и документы на другой базе называются иначе;
- **подпись кнопки берется с формы**: `кнопкаВперед()` возвращает ту, что сейчас
  на мастере помощника, — «Далее >», «Запустить анализ» или «Начать разговор»;
- **кнопка, которая пишет в базу, нажимается только при `можноНажатьДействие()`**,
  иначе шаг снимается без нажатия. `проверитьДействие()` перед выбором действия
  дает понятную ошибку, если его нет.

## Подводные камни

Оба стоили отдельного разбора, поэтому записаны здесь.

**Размер SVG-слоя задается инлайновым стилем в пикселях и с `!important`.**
Атрибуты `width`/`height` — презентационные, и любое правило `svg { ... }` из
стилей 1С их перебивает. Холст тогда молча остается 300x150, все нарисованное
за его границей обрезается, и на снимке просто нет указателя — при этом никакой
ошибки не возникает.

**Слой вешается на `documentElement`**, с максимальным `z-index` и
`pointer-events:none`: так он рисуется поверх модальных окон 1С и не
перехватывает клик следующего шага.

Снимок делается после `waitForTimeout(500)` — иначе в кадр попадает середина
перерисовки.

## Ограничения

- нужна опубликованная база; скрипт проверяет доступность URL и отказывается
  работать вслепую;
- снимки делаются с реальных данных, поэтому собирать инструкцию следует на
  демонстрационной базе: все, что видно на экране, попадет в файл;
- `-ApplyResults` — только на тестовом стенде: с ним сборка записывает
  результат в документы;
- прогон использует настоящего провайдера модели, с обычными лимитами и
  расходом токенов.
