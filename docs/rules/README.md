# Правила разработки 1С — индекс

Общие правила разработки, устанавливаемые комплектом процесса. Читаются **по
требованию**: в контексте агента постоянно живёт только таблица маршрутизации из
блока в `AGENTS.md`, а сами правила лежат файлами и открываются под задачу.

Полный текст правил в `AGENTS.md` не выносится намеренно: набор занимает больше,
чем весь остальной блок вместе с регламентом процесса, и вытеснил бы его из
внимания модели на каждой задаче — включая задачи, где ни одного из этих правил
не требуется.

## Уточнения проекта

Файлы этого каталога принадлежат комплекту процесса и перечислены в
`.1c-workflow.lock.json`. Правка по месту падает на шаге gate
`process-files-unmodified`. Изменение общего правила вносится в репозиторий
комплекта, после чего комплект переустанавливается.

Особенности конкретной конфигурации живут рядом, в
[project/](project/) — этот каталог комплект создаёт один раз и дальше не
трогает. **Прочитав базовый файл, прочитайте одноимённый в `project/`, если он
существует.**

Связь — по имени файла: `project/queries.md` уточняет `queries.md`. Файл, у
которого нет одноимённого базового (`project/naming-prefix.md`), — просто
дополнительное правило проекта.

По умолчанию текст уточнения **добавляется** к базовому. Базовое правило
перестаёт действовать только при явной пометке «Отменяет базовое правило X»
внутри уточнения. Без этой пометки два противоречивых абзаца дают
невоспроизводимый выбор: агент возьмёт любой, и в следующий раз возьмёт другой.

Формат заголовка уточнения и порядок работы с overlay —
[project/README.md](project/README.md). Формат проверяет шаг gate
`rules-overlay-valid`.

## Что в этих правилах, а чего в них нет

Здесь — как писать код и метаданные 1С: стиль, архитектура, запросы, формы,
блокировки, расширения, права.

Здесь **нет** регламента процесса: фазы `Start → Compile → Selfcheck → Verify →
Release`, состав проверок, политика актуализации тестов, изоляция параллельных
задач — всё это в блоке `AGENTS.md` и в
[../1c-development-workflow.md](../1c-development-workflow.md). Правила
разработки не решают, когда работа проверена; это решают фазы.

## Отметки строгости

Часть правил намеренно **строже** стандарта ИТС. Такие правила помечены
`[Правило проекта: строже ИТС]`. В обсуждении и ревью на них ссылаются как на
решение проекта, а не как на требование ИТС; на вопрос — прямо называют разницу.
Ослаблять их «чтобы совпадало с ИТС» молча нельзя: вопрос поднимается, решение
принимает владелец.

## Источник

Набор основан на [comol/ai_rules_1c](https://github.com/comol/ai_rules_1c)
(`content/rules`) и переработан под этот комплект: убрана привязка к чужому
инструментарию и профилям моделей, разделы проверки и приёмки заменены фазами
процесса, значения, специфичные для конфигурации, вынесены в overlay проекта.
