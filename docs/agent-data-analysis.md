# Агентский анализ данных

## Включение

1. Создайте элемент справочника `AI_ПрофилиДоступаКДанным`.
2. Включите `Разрешить выполнение запросов`, если агенту требуется читать данные.
3. Нажмите `Подобрать объекты` и отметьте объекты, которые агенту разрешено читать. Полные имена заполняются автоматически.
4. Для регистров и других больших таблиц включите `Требовать период`.
5. Нажмите `Запретить поля` и отметьте поля, которые модели видеть нельзя. Форма показывает поля только разрешенных объектов, включая поля табличных частей.
6. Укажите профиль в агенте и включите `Агентский режим`.
7. Назначьте пользователю роль `AI_АнализДанныхАгентом` вместе с обычной ролью подсистемы LLM.

Пустой профиль и профиль без разрешения запросов дают модели только инструменты обзора метаданных.

## Модель прав

Роль `AI_АнализДанныхАгентом` разрешает сам механизм выполнения инструментов, но не дает права на прикладные данные. Запрос выполняется без привилегированного режима и дополнительно ограничивается обычными ролями и RLS текущего пользователя.

Для чтения данных одновременно должны выполняться условия:

- у агента выбран профиль;
- в профиле разрешены запросы;
- объект входит в белый список профиля;
- пользователю назначена разрешающая роль;
- у пользователя есть право `Чтение` на прикладной объект.

Белый список и запрет полей проверяются по разбору запроса, а не по его тексту. Схема запроса платформы раскрывает `*`, дописывает имя таблицы к полю без него и переводит английские имена. Затем каждое обращение к полю проходит по доступным полям источника до конца цепочки. Запрещенное поле отклоняется в любой части запроса: в выборке, условиях `ГДЕ` и `ИМЕЮЩИЕ`, соединениях, группировке, сортировке, итогах, параметрах виртуальных таблиц, вложенных запросах и подзапросах `В (...)`. Отбор и сортировка раскрывают значение поля не хуже выборки, поэтому исключений для них нет. Не важно и то, как поле записано: без имени таблицы, через псевдоним (`Т.Цена` из `Документ.Заказ.Товары КАК Т` при запрете `Товары.Цена`), через точку от ссылки (`Заказ.Контрагент.ИНН`) или после `ВЫРАЗИТЬ(... КАК Справочник.Контрагенты)`. Поле виртуальной таблицы регистра наследует запрет поля регистра: запрет `Сумма` закрывает и `СуммаОстаток`, и `СуммаОборот`.

Через точку от ссылки читаются поля только объектов из белого списка, а ссылка на другой объект возвращается только представлением. Если запрещено поле, из которого строится представление ссылки (`Наименование`, `Код`, `Номер`, `Дата`), ссылки на объект приходят без представления, а `ПРЕДСТАВЛЕНИЕ()`, `ПРЕДСТАВЛЕНИЕССЫЛКИ()` и поле `Представление` отклоняются.

`query_execute` выполняет текст, который схема собрала из проверенной структуры, и отдает модели только проверенные колонки. Проверка не видит представление, которое модуль менеджера объекта собирает из других полей (`ОбработкаПолученияПредставления`). Такие сведения закрывайте правами пользователя или не включайте объект в белый список.

## Ограничения запросов

`query_execute` принимает только один запрос выборки языка запросов 1С. Запрещены пакетные запросы, комментарии, временные таблицы, конструкции изменения данных, выборка всех полей (`*`), конструкции компоновки данных в фигурных скобках, `ХАРАКТЕРИСТИКИ` и группирующие наборы. Обычная выборка обязана содержать в верхнем `ВЫБРАТЬ` буквальный `ПЕРВЫЕ N`, не превышающий лимит профиля. Без `ПЕРВЫЕ` разрешены только однострочные агрегаты, состоящие из `КОЛИЧЕСТВО`, `СУММА`, `СРЕДНЕЕ`, `МИНИМУМ` или `МАКСИМУМ`, без группировки, итогов и объединений.

Агент самостоятельно формирует запрос по результатам `metadata_search` и `metadata_describe`, проверяет его через `query_validate`, затем выполняет через `query_execute`. Для вопроса о количестве записей сразу во многих справочниках предназначен `catalog_record_counts`: инструмент обрабатывает все разрешенные справочники или переданный список, возвращает лидеров и не передает модели содержимое элементов. Весь запуск инструмента учитывается как один запрос к данным в лимите профиля; обычные права пользователя и RLS продолжают действовать.

Параметры запроса передаются типизированным массивом. Поддерживаются `string`, `number`, `boolean` и `date`. Для объектов с флагом `Требовать период` обязательны параметры `НачалоПериода` и `КонецПериода`.

Технический аудит вызовов пишется в журнал регистрации с событием `AI.Агент.Инструмент`. Аргументы и строки результата в событие не записываются.

## Диалог в интерфейсе

Пользователь работает с агентом в форме «Диалог с агентом по данным базы»: раздел LLM → «Чат по данным базы». Там агент обязателен, переписка сохраняется в истории диалогов, к сообщению можно приложить файлы, а группа «Шаги агента» показывает вызовы инструментов. Подробно форма описана во встроенной справке (F1).

Для разработчика та же обработка открывает консоль запросов («Еще» → «Консоль запросов»). На ее вкладке `LLM` — лента диалога с отдельным полем нового сообщения. Провайдер, модель, тип API и системная инструкция обязательны; агент здесь опционален.

- без агента выполняется прямой диалог с выбранной моделью без инструментов анализа базы;
- при выборе агента его системная инструкция подставляется автоматически;
- если у агента включен агентский режим, становятся доступны инструменты профиля доступа;
- группа `Ход выполнения` показывает после ответа имя инструмента, статус, длительность, аргументы и результат;
- команда `Сбросить диалог` очищает видимую историю и идентификаторы контекста Chat Completions и Responses API.

Видимая история хранится в открытой форме. Контекст модели между сообщениями поддерживается механизмом диалога API.

## Поддерживаемые API

Многошаговый цикл реализован для:

- OpenAI-совместимого Chat Completions, включая Z.AI и его GLM-модели с tool calling;
- Responses API с продолжением через `previous_response_id` и `function_call_output`.

Лимиты шагов и запросов применяются на один вызов `AI_Клиент.Спросить()`.
