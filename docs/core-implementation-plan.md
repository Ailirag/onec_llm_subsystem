# План развития ядра агентских операций

## 1. Цель

Превратить существующий механизм диалога с агентом в публичное прикладное API,
которое можно безопасно вызывать из документов, обработок, регламентных процессов
и интеграционных расширений.

Целевой режим совместимости расширения: `1С:Предприятие 8.3.25`.

Главный принцип: диалог остаётся одним из потребителей ядра, но перестаёт быть
единственным способом запуска модели.

## 2. Исходная точка

В конфигурации уже существуют два контура выполнения:

- `AI_АгентскиеОперации` обслуживает асинхронный диалог, хранит состояние,
  результат, токены и шаги инструментов;
- `AI_ОчередьЗапросов` является ранним механизмом пакетной обработки и вызывает
  жёстко заданный модуль `AI_ДействияПослеОбработки`.

Каноническим ядром становится `AI_АгентскиеОперации`. Старый регистр очереди не
удаляется в первом цикле: его миграция выполняется после стабилизации нового API.

## 3. Архитектурные сущности

### Агент

Определяет инструкции, набор инструментов, профиль доступа к данным и поведение
модели. Агент не должен содержать прикладной обработчик результата.

### Сценарий

Определяет прикладной контракт вызова: код сценария, агента по умолчанию, схему
входа и выхода, политику повторов и код обработчика. На первом этапе в операции
сохраняется только `КодСценария`; отдельный справочник сценариев добавляется после
стабилизации публичного API.

### Операция

Неизменяемо идентифицируется UUID и хранит состояние одного выполнения. Операция
содержит ссылку на источник, версионированный контекст, идемпотентный ключ,
результат, ошибку и статистику.

### Источник

Для ссылочных объектов универсального CFE используется непосредственно
`ЛюбаяСсылка`. Платформа разрешает определяемые типы в расширениях 8.3.25, но не
разрешает включать в их состав тип-множество `ЛюбаяСсылка`. Во встроенной версии
проекта допустимо заменить поле определяемым типом с перечислением конкретных
ссылок целевой конфигурации. Для записей регистров и внешних сущностей
дополнительно используются строковые поля типа и ключа источника.

## 4. Публичный контракт

Новый общий модуль `AI_ПубличныйAPI` предоставляет только экспортные методы:

```bsl
Параметры = AI_ПубличныйAPI.ПараметрыВыполнения();
Запуск = AI_ПубличныйAPI.НачатьВыполнение(Параметры);
Состояние = AI_ПубличныйAPI.ПолучитьСостояние(Запуск.ИдентификаторОперации);
Результат = AI_ПубличныйAPI.ПолучитьРезультат(Запуск.ИдентификаторОперации);
AI_ПубличныйAPI.Отменить(Запуск.ИдентификаторОперации);
```

Контракт возвращается структурами с именованными свойствами. Новые необязательные
свойства добавляются обратно совместимо. Позиционные параметры не используются.

API должен возвращать версию контракта через `ВерсияИнтерфейса()`.

## 5. Первый вертикальный срез

1. Перевести режим совместимости расширения и донора на 8.3.25.
2. Добавить в операцию необязательный источник типа `ЛюбаяСсылка`.
3. Расширить `AI_АгентскиеОперации` полями:
   - `КодСценария`;
   - `ИдентификаторКорреляции`;
   - `ИдемпотентныйКлюч`;
   - `Источник`;
   - `ТипИсточника`;
   - `КлючИсточника`;
   - `ПредставлениеИсточника`;
   - `ВерсияКонтекста`;
   - `КонтекстJSON`;
   - `Приоритет`.
4. Выделить общий конструктор операции, не требующий создания диалога.
5. Сохранить текущий путь запуска диалога без изменения поведения формы.
6. Добавить прикладной запуск через `AI_ПубличныйAPI`.
7. Реализовать поиск по идемпотентному ключу и возврат существующей операции.
8. Возвращать источник, корреляцию и код сценария в состоянии и результате.
9. Добавить проверки владельца операции и отдельный серверный метод чтения для
   доверенного прикладного обработчика.

## 6. Транзакции и запуск

Запись операции выполняется в транзакции. Фоновое задание запускается только
после её фиксации.

`ЗапуститьНемедленно = Истина` запускает диспетчер после фиксации операции.
Значение `Ложь` позволяет записать outbox в транзакции прикладного объекта.
Откат внешней транзакции откатывает и операцию. Опрос состояния, завершение
обработчика и регламентное задание вызывают диспетчер.

Диспетчер распределяет ограниченное число одновременно работающих заданий:

- захват записи с управляемой блокировкой;
- lease и восстановление зависших операций;
- ограничение параллелизма по провайдеру;
- дата следующей попытки;
- повтор после временных ошибок;
- регламентное задание как механизм восстановления.

Запуск из транзакции записи или проведения документа запрещается. Прикладная
логика должна либо записать outbox-операцию без немедленного запуска, либо вызвать
API после успешного завершения записи объекта.

## 7. Контекст и данные

`КонтекстJSON` содержит только JSON-объект с примитивными значениями, массивами и
вложенными объектами. Обязательное поле верхнего уровня `version` соответствует
`ВерсияКонтекста`.

Запрещено помещать в контекст:

- менеджеры и объекты 1С;
- выборки запросов;
- двоичные данные;
- пароли и API-ключи;
- неограниченные выгрузки прикладных данных.

Вложения хранятся существующим механизмом и связываются с операцией UUID.

## 8. Структурированный результат

После стабилизации первого среза добавляется справочник сценариев и схема ответа.
Поддерживается ограниченный профиль JSON Schema: объекты, массивы, обязательные
поля, простые типы, перечисления и запрет дополнительных свойств.

Адаптер провайдера преобразует внутренний контракт в формат конкретного API.
Полученный JSON повторно проверяется на стороне 1С независимо от проверки модели.

## 9. Доставка результата

Ядро всегда сохраняет результат операции. Callback не является условием
успешного выполнения модели.

Для встроенной подсистемы используется переопределяемый диспетчер обработчиков.
Для самостоятельного CFE результат доступен через опрос публичного API; отдельное
интеграционное расширение может сопоставить белый список кодов обработчиков с
экспортными методами основной конфигурации.

Произвольный вызов имени общего модуля из пользовательских данных не допускается.
Доставка результата должна быть идемпотентной и иметь собственный статус ошибки.

## 10. Безопасность

- При создании операции повторно проверяется доступ пользователя к агенту.
- В операции сохраняется инициатор и фактически применённый профиль доступа.
- Пользователь читает и отменяет только собственные операции.
- Привилегированный режим не должен обходить проверку владельца и профиля.
- Технический обработчик получает только документированный результат операции.
- Контекст, результат и журнал имеют настраиваемые сроки хранения.

## 11. Тестирование

Для каждого этапа обязательны:

- структурная проверка XML и CFE;
- загрузка расширения в чистую тестовую базу;
- обновление конфигурации базы данных;
- проверка применимости расширения;
- тест конструктора параметров публичного API;
- тест идемпотентного повторного запуска;
- тест запрета чтения чужой операции;
- тест диалога без изменения существующего поведения;
- тест успешного ответа имитатора HTTP-провайдера;
- отдельный smoke-тест реальной модели провайдера перед выпуском.

## 12. Этапы поставки

### P0. Основание ядра

Режим 8.3.25, источник операции, публичный API, корреляция,
идемпотентность и обратная совместимость диалога.

### P1. Диспетчер очереди

Ограниченный пул фоновых заданий, приоритеты, lease, повторы, восстановление и
очистка завершённых операций.

### P2. Сценарии и структурированный ответ

Справочник сценариев, версия схемы, адаптеры `response_format`, локальная проверка
результата и безопасная доставка обработчику.

### P3. Обратная связь и наблюдаемость

Вердикты пользователей, метрики очереди, длительности этапов, версии промптов и
отчёт об ошибках доставки.

### P4. Миграция legacy-очереди

Перевод потребителей `AI_ОчередьЗапросов` на публичный API и удаление жёсткой
лесенки `AI_ДействияПослеОбработки` после периода совместимости.

## 13. Критерий готовности первого среза

Первый срез завершён, когда прикладной код может поставить операцию без создания
диалога, получить UUID, безопасно опросить состояние и результат, а существующая
форма диалога проходит прежний smoke-тест. Повторный вызов с тем же
идемпотентным ключом не создаёт вторую операцию.

## 14. Текущий статус реализации

Реализован первый вертикальный срез P0:

- публичный API прикладного запуска без создания диалога;
- источник, корреляция, код сценария, приоритет и версионированный JSON-контекст;
- строгая идемпотентность под управляемой блокировкой;
- передача прикладного контекста в модель;
- сохранение прежнего пути диалога и проверок доступа к агенту;
- восстановление исходного привилегированного режима после публичных вызовов;
- отдельный функциональный тест публичного API и регрессионный smoke-тест.

Добавлен вертикальный срез P1:

- глобальный и провайдерский лимиты параллелизма нового ядра;
- приоритет очереди, атомарный захват и токен попытки;
- отмена незапущенной операции без ожидания таймаута;
- запрет двойного запуска одного обработчика;
- восстановление истекшей аренды: незапущенная операция возвращается в очередь,
  прерванная начатая операция получает ошибку с неизвестным внешним результатом;
- явно разрешенные повторы HTTP 429/502/503/504 до выполнения инструментов
  и без вложений, с задержкой и ограничением числа попыток;
- накопление токенов всех попыток;
- очистка контекста, промптов, результата и шагов старых прикладных операций
  с сохранением идентификатора, статистики и идемпотентного ключа.

### Эксплуатационные условия P1

1. Диспетчер запускает только операции текущего пользователя. Это сохраняет
   права инициатора: фоновый процесс не подменяет его администратором.
2. Для безусловного обслуживания отложенных операций без опроса клиентом нужно
   настроить расписание `AI_ДиспетчерОпераций` от имени их инициатора.
   Пользовательское регламентное задание не является универсальным диспетчером
   всех пользователей. Массовое обслуживание разных инициаторов требует
   отдельного проектирования серверного контекста безопасности.
3. Ограничения параллелизма охватывают новое ядро. Старую пакетную очередь и
   прямые вызовы `AI_Клиент` они пока не охватывают; объединение относится к P4.
4. `AI_СрокХраненияОперацийДней = 0` отключает очистку. Положительное значение
   очищает данные прикладных операций, но не историю диалогов и не двоичные
   вложения: для них действуют отдельные механизмы хранения.
5. По истечении срока публичный API возвращает `ДанныеОчищены = Истина`.
   Повтор идемпотентного ключа не выполняет модель заново.
6. Автоматический повтор по произвольному тексту ошибки, таймауту транспорта
   или после неизвестного результата инструмента запрещен.

Добавлены серверные срезы P2/P3/P4:

- `AI_Сценарии`: агент и модель по умолчанию, версия контракта, JSON Schema,
  код обработчика, политика повторов; схема и код обработчика копируются в операцию;
- Responses `text.format` и Chat Completions `response_format`, строгая локальная
  проверка ответа; ошибка схемы не теряет ответ и израсходованные токены;
- отдельное непривилегированное задание доставки, транзакционный статический
  обработчик, отдельный статус ошибки и ручной повтор без повторного вызова модели;
- неизменяемые события оценки пользователя с исходным и исправленным ответом,
  идемпотентный UUID оценки, персональная статистика и список ошибок доставки;
- дата первого запуска и SHA-256 системной инструкции, отдельный срок хранения
  текстов обратной связи;
- opt-in маршрут старого метода очереди через сценарий, явный атомарный перенос
  новых записей, статус `ПеренесенВЯдро` и ссылка на новую операцию.

### Границы выполненного среза

- Добавлена форма `AI_МониторАгентскихОпераций`: последние личные операции,
  результат, персональная статистика, ошибки доставки, повтор доставки и
  сохранение решения `Принято` / `Отклонено` / `Исправлено`.
- Оценка относится к прикладной операции. Она намеренно не встроена в обычный
  чат, у которого отдельная модель хранения бесед и сообщений.
- Схема входа пока ограничена JSON-контекстом с обязательной версией, отдельная
  JSON Schema входа не реализована.
- Профиль JSON Schema намеренно ограничен; неизвестные ключевые слова отклоняются.
  Поддержка schema конкретной моделью проверяется ее API, автоматического fallback
  в обычный текст нет.
- Доставка рассчитана на короткие локальные записи 1С в общей транзакции.
  Произвольные HTTP-побочные эффекты и произвольные имена методов не поддерживаются.
- Старые обработчики не удалены до миграции потребителей. Перенос вложений старой
  очереди требует отдельного адаптера и сейчас явно отклоняется.
- Рабочие данные автоматически не мигрировались. Рабочая база не обновлялась.

Контракт интеграции и примеры: [core-api.md](core-api.md).

### Проверки Ядра

Проверено на платформе 8.3.27.2130 с режимом совместимости 8.3.25:

- загрузка CFE в отдельную базу, применимость и синтаксис ThinClient,
  WebClient, Server, ExternalConnection;
- десять регрессионных smoke-тестов с HTTP-имитатором;
- публичный вызов, идемпотентность, доставка JSON-контекста и учет токенов;
- слоты очереди, запрет чтения/отмены чужой операции, отмена до запуска,
  двойной обработчик, восстановление прерванной операции, откат outbox,
  HTTP 503 с пределом попыток, очистка данных;
- отдельный запуск через клиент 1С: операция реально выполнена фоновым заданием
  и получен `MOCK_AGENT_OK`, прямой вызов обработчика в этом тесте отключен;
- снимок сценария, строгая схема, оба адаптера API, ошибка доставки отдельно от
  результата, успешный callback без привилегий, откат callback и повтор доставки;
- сохранение и идемпотентность оценок, запрет перезаписи события, статистика и
  очистка текстов без потери вердикта;
- атомарный перенос legacy-записи, повторный перенос без дубликата, невозможность
  старого захвата после переноса и запрет переноса уже захваченной записи;
- opt-in маршрут старого метода с получением ответа модели;
- Web UI smoke открыл диалог и монитор операций и сохранил оценку через форму;
- реальная модель Yandex DeepSeek через публичный API нового ядра вернула `OK`:
  100 входных и 35 выходных токенов. Прогон выполнен в изолированной копии базы
  синхронным worker-путем; исходная рабочая база не изменялась.

Проектный workflow-preflight не установлен в репозиторий, поэтому его фаза
`Finish` не запускалась. Эквивалентные доступные проверки исходников, применимости,
модулей, функционального контура и Web UI пройдены отдельно. Проверка на отдельном
бинарном релизе платформы 8.3.25 остается выпускным условием.
