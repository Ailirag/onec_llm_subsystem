# Журналирование

**Когда читать:** когда задача требует записи в журнал регистрации, и при любой
правке обработки ошибок.

[code-style.md](code-style.md) запрещает `ЗаписьЖурналаРегистрации()` без
требования задачи и пустой обработчик исключения. Этот файл — положительная
сторона: когда журналирование запрошено, вот как его делать.

## Что журналировать

| Событие | Писать | Что включать |
|---|---|---|
| Исходящий запрос интеграции (HTTP, SOAP, очередь) | да | адрес, метод, код состояния, время ответа, идентификатор корреляции. Тело запроса — только если в нём нет ПДн и учётных данных |
| Входящий вебхук, регламентный обмен | да | источник, размер полезной нагрузки, принято или отклонено, причина отказа |
| Фоновые и регламентные задания | да | старт и финиш, результат, ключевые параметры. Необходимо потому, что у пользователя нет обратной связи в интерфейсе |
| Отказ проведения (`Отказ = Истина`) | да | документ, организация, бизнес-причина. Пользователь ошибку уже увидел, но журнал — единственное место, где она сохранится |
| Откат транзакции | да | причина и ключ операции |
| Обычные создание, изменение, удаление через интерфейс | нет | достаточно штатного аудита платформы |
| Исключение, поймано внешним обработчиком | да | полное `ПодробноеПредставлениеОшибки(ИнформацияОбОшибке())` |
| Отладочный вывод во время разработки | нет | отладчик; убрать до коммита |

Правило: **журналировать то, что нельзя восстановить позже.** Ошибки, которые
видел пользователь, границы интеграций, фоновая работа. Не журналировать обычные
чтения и записи, которые и так оставляют след в метаданных.

## Уровни

| Уровень | Для чего |
|---|---|
| `Ошибка` | операция не выполнена, состояние несогласованное или требует разбора. Уходит в мониторинг |
| `Предупреждение` | операция выполнена по деградированному пути: повтор удался, использован обходной вариант, необязательная зависимость недоступна. Не поднимает дежурного, но попадает в сводку |
| `Информация` | значимое для бизнеса событие, которое завершилось успешно: завершённый обмен, завершённое фоновое задание, изменение состояния, достойное аудита |
| `Примечание` | диагностическая деталь. В производственном коде — редко; лучше не писать вовсе, чем создавать шум |

Уровни — контракт с мониторингом, а не оттенки настроения: `Ошибка` обязана быть
тем, на что реагируют.

## Имена событий

События журнала фильтруются по имени. Имя иерархическое, через точку:

```
<Подсистема>.<Операция>.<Исход>
```

Примеры:

- `Интеграция.ОбменССРМ.Запрос`
- `Интеграция.ОбменССРМ.Ответ`
- `Интеграция.ОбменССРМ.Ошибка`
- `Проведение.РеализацияТоваровУслуг.КонфликтБлокировки`
- `ФоновоеЗадание.ОбновлениеКурсовВалют.Старт`
- `ФоновоеЗадание.ОбновлениеКурсовВалют.Финиш`

Префикс `Debug.*` — только на время активной отладки, и обязательно убирается до
коммита. В выпуск `Debug.*` не попадает.

## Структурированные данные

Когда у события есть контекст, передавать его **структурой** в параметре `Данные`.
Склеенная строка не разбирается ни фильтром журнала, ни внешним приёмником.

```bsl
ДанныеСобытия = Новый Структура;
ДанныеСобытия.Вставить("Документ", СсылкаДокумента);
ДанныеСобытия.Вставить("Организация", ОрганизацияДокумента);
ДанныеСобытия.Вставить("ДлительностьМс", Длительность);
ДанныеСобытия.Вставить("КодСостояния", ОтветHTTP.КодСостояния);

ЗаписьЖурналаРегистрации(
	"Интеграция.ОбменССРМ.Ответ",
	УровеньЖурналаРегистрации.Информация,
	Метаданные.Документы.РеализацияТоваровУслуг,
	СсылкаДокумента,
	"",
	ДанныеСобытия);
```

- **Имя события** — иерархическое, из раздела выше.
- **Уровень** — из таблицы уровней.
- **Метаданные** — объект, к жизненному циклу которого относится событие.
  Передавать для событий записи и проведения; для сквозных событий вроде
  жизненного цикла регламентного задания оставлять `Неопределено`.
- **Данные-источник** — конкретная ссылка. Позволяет отфильтровать журнал до одной
  сущности одним действием.
- **Комментарий** — короткий свободный текст. Пустая строка, если структура уже
  несёт всё.
- **Данные** — структура.

Не читать реквизиты объекта только для того, чтобы собрать данные события: чтение
ради журнала — это чтение из базы, оплаченное диагностикой, которая может никогда
не понадобиться.

## Ошибки и исключения

Внутри обоснованного `Попытка ... Исключение` ошибка записывается **один раз**, с
полным описанием:

```bsl
Попытка

	ВыполнитьИнтеграционныйЗапрос();

Исключение

	ДанныеОшибки = Новый Структура;
	ДанныеОшибки.Вставить("Подробно", ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));
	ДанныеОшибки.Вставить("Адрес", АдресСервиса);

	ЗаписьЖурналаРегистрации(
		"Интеграция.ОбменССРМ.Ошибка",
		УровеньЖурналаРегистрации.Ошибка,
		,
		,
		НСтр("ru = 'Не удалось выполнить запрос к внешнему сервису.'"),
		ДанныеОшибки);

	ВызватьИсключение;

КонецПопытки;
```

- **`ПодробноеПредставлениеОшибки`**, а не `КраткоеПредставлениеОшибки`: краткое
  теряет стек и причину.
- **После записи возбуждать исключение снова**, если контракт прямо не требует
  проглотить конкретный код ошибки. Молчаливое «записал и продолжил» — самая частая
  причина расхождений данных, которые потом никто не может объяснить.
- **Не писать дважды.** Если внутренний обработчик уже записал уровень `Ошибка`,
  внешний пишет максимум `Предупреждение` («операция прервана из-за <причина>») и
  не дублирует `Подробно`.

## Что в журнал не попадает

- **Учётные данные**: пароли, токены, ключи API, секреты OAuth, cookie сеанса —
  включая содержимое `Подробно`. Маскировать до записи.
- **Персональные данные на уровне тела запроса**: паспорт, СНИЛС, карта, списки
  адресов. Писать идентификатор записи или хеш, не значение. Какие поля проект
  считает персональными данными, фиксируется в `docs/rules/project/logging.md`:
  нейтральный комплект этого знать не может.
- **Большие двоичные данные и вложения.** Писать метаданные — размер, тип, ключ
  хранения, — не байты.
- **Таблицу значений целиком.** Писать сводку: количество строк, ключевые колонки.

## Ротация

Журнал регистрации по умолчанию не ограничен. Для систем с заметным объёмом
настраивать разделение по периодам и периодически сокращать журнал регламентным
заданием, а старые срезы архивировать. При наличии внешнего мониторинга —
периодическая выгрузка во внешний приёмник и очистка на стороне платформы.
Потоковая телеметрия в реальном времени — не задача журнала регистрации, для этого
существует технологический журнал.
