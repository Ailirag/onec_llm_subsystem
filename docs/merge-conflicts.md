# Конфликты слияния в выгрузке 1С

Документ обязателен к применению при параллельной разработке. Он описывает, как
разрешать конфликты в XML-выгрузке так, чтобы не потерять чужую доработку.

## Почему для 1С это отдельная тема

Ниже `<src>` — каталог исходников конфигурации из `sourceDir` в `.1c-workflow.json`
(в этом проекте — `conf`), а `<ext>` — каталог исходников расширения.

В обычном коде неудачно разрешённый конфликт почти всегда ломает сборку. В
выгрузке 1С это не так: конфигурация состоит из двух независимых представлений
одного и того же факта — **объявления** в `<src>/Configuration.xml` и **файла**
объекта, например `<src>/Catalogs/ОчередиТрекера.xml`. Если при слиянии потерялась
строка объявления, то:

- файл объекта остаётся в Git и в diff ничего подозрительного не видно;
- платформа загружает конфигурацию **без ошибок**;
- объект просто исчезает из конфигурации вместе со всей логикой.

Именно поэтому в preflight встроен шаг `source-integrity`
([scripts/workflow/Test-SourceIntegrity.ps1](../scripts/workflow/Test-SourceIntegrity.ps1)),
который сверяет объявления с файлами на диске в обе стороны. Без него такой
дефект доходит до `main`.

## Обязательный порядок работы

1. **Только rebase, никогда merge** в задачную ветку:

   ```powershell
   git fetch origin
   git rebase origin/main
   ```

   Merge-коммиты в задачной ветке делают историю выгрузки нечитаемой и повторно
   поднимают уже разрешённые конфликты при каждом следующем слиянии.

2. Разрешить конфликты по правилам ниже.

3. **Обязательно** прогнать проверку целостности до любых других действий:

   ```powershell
   powershell.exe -NoProfile -ExecutionPolicy Bypass `
     -File scripts\workflow\Test-SourceIntegrity.ps1
   ```

4. Затем — штатный автомат задачи: `Compile`, потом без новых изменений `Selfcheck`.
   Успешный `Compile` после ручного разрешения конфликта — не формальность:
   `-CompileOnly` загрузка ловит структурные ошибки XML.

## Правила по файлам

| Файл | Природа конфликта | Как разрешать |
|---|---|---|
| `<src>/Configuration.xml` → `ChildObjects` | Двое добавили разные объекты | Сохранить **обе** строки. Порядок внутри вида метаданных значения не имеет, дубли запрещены |
| `<src>/Configuration.xml` → `Version` | Двое подняли версию | Взять версию из `origin/main`. Версию поднимает только фаза `Release`, задачная ветка её не меняет |
| `<src>/Configuration.xml` → `DefaultRoles`, `Languages`, `Subsystems` | Двое зарегистрировали разное | Сохранить обе записи, затем проверить целостность |
| `<src>/Subsystems/**/*.xml` → `Content` | Двое включили разные объекты в подсистему | Сохранить обе ссылки. Порядок определяет порядок команд в интерфейсе — согласовать с автором второй половины |
| `<src>/Roles/**/Ext/Rights.xml` | Двое выдали права на разные объекты | Разрешать **поблочно** по `<object>`. Никогда не брать сторону целиком: это молча снимет права, выданные коллегой |
| `<src>/**/Forms/**/Ext/Form.xml` | Двое правили одну форму | **Не разрешать вручную.** Взять версию из `origin/main`, затем воспроизвести своё изменение в Конфигураторе и снять его через `Import-DesignerChanges.ps1`. Ручное слияние `Form.xml` по id-атрибутам приводит к неработающей форме |
| `<src>/**/Ext/*.bsl` | Обычный конфликт кода | Разрешать как обычный код |
| `<src>/**/Ext/Predefined.xml` | Двое добавили предопределённые элементы | Сохранить обе записи, следить за уникальностью имён |
| `artifacts/**` (CF/CFE, `manifest.json`) | Двое собрали релиз | Артефакты создаются только фазой `Release` из чистой `main`. В задачной ветке конфликт здесь означает, что артефакты попали в ветку по ошибке — откатить их |

## Запрещено

- Разрешать конфликты в XML-выгрузке через `git checkout --ours` / `--theirs`
  для файла целиком, кроме явно разрешённого случая с `Form.xml`.
- Настраивать `merge=union` для файлов выгрузки: он молча склеивает XML в
  невалидную структуру, а для `Rights.xml` — в неверные права.
- Коммитить файл с маркерами `<<<<<<<` / `>>>>>>>`. Это ловит и локальный
  `source-integrity`, и CI-gate.
- Объявлять задачу готовой без успешного `Compile` после разрешения конфликтов.

## Как снизить число конфликтов

- Одна форма, одна роль, одна подсистема — один автор в один момент времени.
  Это организационное правило, а не техническое: XML-выгрузка формы не
  предназначена для параллельного редактирования.
- Дробить задачи так, чтобы они не пересекались по объектам метаданных.
- Делать `git fetch && git rebase origin/main` в начале дня, а не перед MR:
  один большой rebase болезненнее нескольких мелких.
- Крупные изменения командного интерфейса согласовывать заранее — они почти
  всегда затрагивают `Configuration.xml` и подсистемы, то есть конфликтуют со
  всеми параллельными задачами.
