# Наборы знаний для агентов и сценариев

## Решение

Дополнительные контексты объединяются в отдельный справочник «Наборы знаний».
Набор содержит упорядоченный список существующих карточек дополнительного
контекста и собственные признаки активности, версии и актуальности. Агент и
сценарий получают ссылки на наборы отдельными табличными частями; одиночные
карточки сохраняются для точечной настройки и обратной совместимости.

При подготовке запроса знания раскрываются в общий плоский список. Сначала
применяются знания агента, затем знания сценария. Повтор карточки удаляется, а
карточка сценария с тем же программным идентификатором перекрывает карточку
агента. Такой порядок делает локальную настройку сценария предсказуемым
уточнением базовой настройки агента.

## Почему так

Отдельный агент ради фиксированного набора контекстов не нужен: агент остаётся
исполнителем с поведением и инструментами, а набор знаний является повторно
используемой конфигурацией контекста. Один дополнительный шаг сценария также не
подходит как основная модель, потому что знания нужны до выполнения разных
шагов и должны одинаково назначаться нескольким агентам и сценариям.

Новые тексты не копируются внутрь агента или сценария. Ссылки на карточки
сохраняют единый источник данных, позволяют обновлять банковские реквизиты и
карточку предприятия один раз и применять новую версию во всех назначениях.

## Совместимость и контроль

Существующие одиночные контексты продолжают работать. Для нового справочника и
изменённых форм добавлены права, встроенная F1-справка и функциональные
проверки. Пошаговая инструкция имеет паспорт и входит в релизный цикл
документации; отсутствие F1-справки у нового пользовательского объекта
останавливает фазу Compile.

# Укрепление MCP-контура

## Решение

MCP-клиент остается частью расширения и поддерживает два поколения протокола:
современный stateless-контур `2026-07-28` с `server/discover` и прежний
handshake-контур до `2025-11-25`. Выбор поколения выполняется автоматически на
один вызов; современный запрос несет версию и возможности клиента в `_meta`, а
HTTP-заголовки содержат маршрут метода и инструмента.

Секреты MCP доступны только серверному модулю внутри краткой привилегированной секции. Прикладные
роли не получают права чтения регистра секретов, а наружу модуль возвращает
секрет только непосредственно транспортному клиенту. Значения секретов,
аргументы и результаты инструментов не записываются в диагностику.

Контур проверяется детерминированным mock-сервером: подключение, согласование
версии, пагинация `tools/list`, авторизация, синхронизация, прямой `tools/call` и
полный цикл агента выполняются на функциональном стенде. Проверка прав на секреты
добавляется как статический контракт тестового адаптера.

## Рассмотренные варианты

- Хранить секрет в карточке сервера отвергнуто: пользователь с правом просмотра
  карточки получил бы значение через обычное чтение объекта.
- Оставить чтение регистра прикладным ролям отвергнуто: скрытое поле формы не
  является границей безопасности.
- Перевести хранение на методы безопасного хранилища БСП отвергнуто для этой
  версии: расширение должно загружаться и в минимальную тестовую конфигурацию без
  БСП. Используется рекомендованный для конфигураций без БСП отдельный объект с
  минимальными правами и серверным фасадом, который включает привилегированный режим только на операцию с секретом. Метаданное свойство `Privileged` для общего модуля расширения платформой запрещено.
- Поддерживать только handshake-поколение отвергнуто: актуальные MCP-серверы
  вправе не принимать `initialize`.
- Считать режим «Подтверждать» автоматическим отвергнуто. Пока нет устойчивого
  продолжения фонового агентского запуска после ответа пользователя, режим
  остается fail-closed и не передает инструмент модели.
- Автоматически проходить OAuth в фоне отвергнуто: это отдельный интерактивный
  поток с redirect URI, refresh-token и политикой выдачи согласия. Текущая
  карточка честно поддерживает только явно выбранные статические способы
  авторизации.

## Влияние на соседние контуры

Пользовательские роли теряют прямое чтение технического регистра секретов, но
вызовы разрешенных MCP-инструментов продолжают работать через серверный
фасад. Старые MCP-серверы сохраняют совместимость. Mock-провайдер функциональных
тестов получает MCP-маршруты, но существующие маршруты модели и RAG не меняются.

## Чего решение не делает

Решение не реализует OAuth-клиент, постоянные SSE-подписки, server-initiated
sampling и интерактивное продолжение MRTR. Эти возможности не объявляются
клиентом; запрос дополнительного ввода завершается явной диагностируемой ошибкой,
а не выполняется без согласия.
