# Проектирование регистров

**Когда читать:** при создании и при перестройке регистра сведений, накопления,
бухгалтерии, расчёта.

Регистры — несущая конструкция конфигурации, и ошибка здесь дорога: она вплетена в
проведение документов, в RLS и в отчёты. Решения ниже принимаются **до** создания
объекта.

Запросы к регистрам — [queries.md](queries.md). Блокировки при проведении —
[locks.md](locks.md). Отчёты — [dcs.md](dcs.md).

## Выбор типа регистра

| Тип | Когда подходит | Когда не подходит |
|---|---|---|
| `РегистрСведений` | произвольные данные по ключу измерений, с периодичностью или без: настройки, соответствия, кешированные значения, история реквизитов, статусы обменов и длительных операций | данные являются приращением, которое надо суммировать как остатки или обороты |
| `РегистрНакопления` (остатки) | остаток на момент времени: склад, задолженность, резервы. Регистр отвечает на вопрос «сколько сейчас / на дату X» | данные никогда не спрашивают как остаток |
| `РегистрНакопления` (только обороты) | оборот за период, который никогда не спрашивают как остаток: продажи за период, трафик | вопрос об остатке реалистичен: возврат остатков позже стоит полной переделки |
| `РегистрБухгалтерии` | двойная запись по плану счетов | абстракция двойной записи навязывается там, где её нет |
| `РегистрРасчета` | перерасчёт по периоду регистрации и периоду действия, зависимости между видами расчёта | всё, что не является расчётом зарплаты и подобных начислений |

Проверочный вопрос: **может ли пользователь спросить остаток на дату?** Да —
регистр накопления. Нет, это просто типизированный поиск по ключу — регистр
сведений. Остальное требует отдельного разбора; начинать с регистров бухгалтерии
или расчёта по привычке — ошибка.

## Измерения

- **Сначала избирательность.** Измерения с высокой кардинальностью и узким
  отбором ставить первыми (`Контрагент`, `Договор`, `Номенклатура`),
  низкокардинальные (`Организация`, `Подразделение`) — после. Порядок влияет на
  использование индекса в запросах к виртуальным таблицам.
- **Устойчивая идентичность, не свободный текст.** Измерения — ссылочных типов,
  перечисления, дата для периодических. Строки и числовые коды как измерения
  ветвят данные на каждой опечатке.
- **Периодичность** — самая грубая из тех, что ещё отвечает на бизнес-вопрос:
  непериодический (константы, соответствия, текущие значения), в пределах секунды
  (движения), в пределах дня (курсы, журналы статусов), в пределах месяца или года
  (планирование). Более тонкая периодичность раздувает таблицу и замедляет всё.
- **Ведущее измерение** ставить только когда удаление объекта должно каскадно
  удалить запись регистра. По умолчанию измерение ведущим не является.

## Ресурсы

- Ресурсы количественные и суммируемые. Для регистра накопления это обязательно.
- **Один ресурс — одна единица измерения.** Сумма в разных валютах в одном ресурсе
  — ловушка: либо ресурс на валюту, либо валюта измерением.
- Отрицательные значения для регистров накопления осмысленны (возвраты,
  списания). Для регистров сведений — обычно признак ошибки проектирования, кроме
  явно знаковых величин.

## Реквизиты

Реквизиты — неагрегируемые данные, которые едут вместе с записью (`Комментарий`,
`НомерЗаказа`). Они не индексируются, и отбирать по ним в интенсивных запросах
нельзя. Если отбор по реквизиту повторяется — это измерение, а не реквизит.

## Индексирование

- Помечать измерение `Индексировать` только когда оно участвует в запросах и в
  параметрах виртуальных таблиц **без** всех предшествующих измерений. Первому
  измерению явный индекс не нужен: платформа строит его сама.
- Не индексировать всё «на всякий случай»: каждый индекс замедляет запись.

## Подчинение регистратору

- Для регистров накопления **подчинение регистратору — состояние по умолчанию**:
  регистр наполняется движениями документов из `ОбработкаПроведения`.
- Независимый регистр сведений — для данных без документа-источника: настройки,
  соответствия, текущие значения.
- Смешанный режим для регистра сведений применяется в журналах статусов; считать
  его нетиповым решением и обосновывать в описании объекта.

## Виртуальные таблицы

| Таблица | Назначение |
|---|---|
| `Остатки(&Период, Условие)` | остаток на `&Период` по отбору |
| `Обороты(&НачалоПериода, &КонецПериода, ..., Условие)` | оборот за период |
| `ОстаткиИОбороты(...)` | начальный остаток, оборот и конечный остаток одним запросом |
| `СрезПервых(&Период, Условие)` | первая запись на дату или после (регистр сведений) |
| `СрезПоследних(&Период, Условие)` | последняя запись на дату или до (регистр сведений) |

Отбор передавать параметром виртуальной таблицы, не условием `ГДЕ` после вызова.
Параметр уходит внутрь движка и использует индексы; `ГДЕ` сначала читает
виртуальную таблицу целиком.

Для вопросов об остатках и оборотах использовать виртуальные таблицы, а не свою
агрегацию по физической таблице. «Последнее значение» для периодического регистра
брать `СрезПоследних`, а не `ПЕРВЫЕ 1 ... УПОРЯДОЧИТЬ ПО ... УБЫВ`.

## Проведение и перепроведение

- `ОбработкаПроведения` живёт в модуле объекта документа. Внутри порядок:
  **заблокировать, прочитать, записать** — [locks.md](locks.md). Диалогов,
  длительных операций и обращений к внешним сервисам внутри нет.
- `Движения.X.Записывать = Истина` устанавливать один раз, не переключать в цикле.
- **Движения не менять вне `ОбработкаПроведения` и
  `ОбработкаУдаленияПроведения`.** Прямая правка `Движения.X` из обработки обходит
  логику последовательностей и оставляет несогласованные данные.
- Массовое перепроведение — выборкой документов и `Записать(РежимЗаписиДокумента.Проведение)`
  с транзакцией на документ и явной обработкой отказов. Одна транзакция на тысячи
  документов эскалирует блокировки и останавливает кластер.
- Когда важен порядок между документами, использовать `Последовательность`, а не
  надеяться на порядок вставки.

## Изменение состава ключа

Удаление или сужение части **ключа** — измерения регистра сведений, реквизита в
ключе, уникального индекса — необратимо теряет данные: записи, различавшиеся
только удаляемой частью, реструктуризация схлопнет в одну молча, без записи в
журнале регистрации. Зелёные фазы этого не поймают: на стенде продуктивных данных
нет.

Обязательный порядок действий описан в блоке процесса в `AGENTS.md` (проверка
запросом на продуктивных данных, склейка **предыдущим** выпуском либо
зафиксированная владельцем потеря). Здесь важно другое: на этапе проектирования
состав ключа выбирается так, чтобы его не приходилось сужать.

## RLS

- Ограничения доступа к регистрам строятся по той же схеме, что для справочников и
  документов.
- Для регистра, связывающего несколько типовых объектов измерениями, шаблон
  ограничения разрастается: повторяющиеся условия выносить в переиспользуемый
  предикат через подсистему управления доступом БСП.
- Проверять ограничение под неадминистративной ролью до слияния: роль с полными
  правами обходит RLS и скрывает дефект.
