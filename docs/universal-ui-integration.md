# Универсальная интерфейсная интеграция

Механизм позволяет запускать настроенные AI-сценарии из прикладного контекста,
не добавляя в подсистему ссылок на документы и справочники конкретной
конфигурации.

## Состав

- `AI_МестаЗапускаСценариев` хранит соответствие места интерфейса и сценария;
- `AI_ИнтерфейсныеСценарии` формирует переносимый снимок контекста и проверяет
  доступность действий;
- `AI_ПомощникКонтекста` показывает пользователю подходящие действия и
  открывает существующий асинхронный диалог;
- `integrations/bsp/AI_ПомощникКонтекстаБСП` содержит исходники внешней
  обработки для механизма дополнительных обработок БСП.

Обычная ссылка прикладной конфигурации не сохраняется в данных подсистемы.
В диалог и агентскую операцию передаются полное имя метаданных, UUID ссылки,
представление и версионированный JSON-снимок. Поэтому каноническое расширение
не заимствует прикладные объекты.

## Настройка администратора

1. Создать и активировать агента и сценарий.
2. Настроить доступ пользователей или групп к агенту.
3. Создать элемент `Места запуска сценариев`.
4. Выбрать сценарий, тип места и полное имя метаданных, например
   `Документ.ДоговорКонтрагента`.
5. Указать представление команды, описание и начальный запрос.
   Представление команды попадает в заголовок окна помощника.
6. При необходимости разрешить обработку нескольких выбранных объектов
   и выбрать режим выполнения (по умолчанию — очередь, по операции на объект).

Пустое полное имя или `*` означает любое метаданное соответствующего типа
места. Тип `Глобально` используется для команды подсистемы без прикладного
объекта. Пользователь видит только действия, чей агент ему доступен.

### Установка расширения

Платформа ставит новое расширение с включенным безопасным режимом, а в нем
запрещен конструктор `HTTPСоединение` — подсистема не сможет обратиться ни к
одной модели и упадет с «Установлен безопасный режим. Выполнение операции
запрещено». После загрузки расширения безопасный режим и защиту от опасных
действий нужно снять: в конфигураторе — «Администрирование → Расширения
конфигурации», из кода — через `РасширенияКонфигурации.Получить()`
(`БезопасныйРежим = Ложь`), либо ключом `--safe-mode=no` у `ibcmd extension
update`.

## БСП

Внешняя обработка регистрируется с видом `ЗаполнениеОбъекта` и клиентским
вызовом. БСП передает массив выбранных ссылок, после чего подсистема сама
фильтрует доступные сценарии.

Назначение обработки собирается по активным местам запуска с типом `Объект`
или `Список`: в назначение попадают только те метаданные, для которых
действительно настроено действие. Перебор всех документов, справочников,
бизнес-процессов и задач остается запасным вариантом и включается, только если
хотя бы одно место разрешено для любого метаданного (пустое имя или `*`) либо
справочник мест недоступен на чтение. Это важно для больших конфигураций:
иначе команда появилась бы в меню заполнения у сотен объектов.

### Где лежит обработка

Исходники — в `integrations/bsp/AI_ПомощникКонтекстаБСП.xml`. Собранный файл
дополнительно хранится внутри расширения макетом
`DataProcessor.AI_ПомощникКонтекста.Template.ОбработкаБСП`, поэтому переносится
вместе с подсистемой и не теряется при установке в другую базу.

Выгрузить встроенную копию можно командой «Сохранить обработку для БСП» на
форме помощника либо программно:

```bsl
ДвоичныеДанные = AI_ИнтерфейсныеСценарии.ПолучитьВстроеннуюОбработкуБСП();
Адрес = AI_ИнтерфейсныеСценарии.АдресВстроеннойОбработкиБСП(ИдентификаторФормы);
```

Макет — двоичная копия, она не пересобирается сама. После правки исходников
обработки прогоните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools\Build-BspDataProcessorTemplate.ps1
```

Скрипт собирает EPF навыком `epf-build` и кладет результат в макет. Сборку
надо выполнять в базе, где подсистема уже установлена: обработка сознательно
вызывает ее общий клиентский модуль и читает справочник мест запуска.

## API адаптера

Если типовая конфигурация не передает нужный контекст через БСП, небольшой
адаптер вызывает клиентский метод:

```bsl
AI_ИнтерфейсныеСценарииКлиент.ОткрытьПомощник(
    МассивСсылок,
    "Объект");
```

Для глобального запуска используется
`AI_ИнтерфейсныеСценарииКлиент.ОткрытьГлобальныйПомощник()`.

Адаптер отвечает только за получение корректных ссылок из формы. Выбор
сценария, проверка доступа, подготовка контекста и открытие диалога остаются в
ядре подсистемы.

## Действия с результатом

Что делать с тем, что предложила модель, решает не код помощника, а настройка:
у места запуска есть реквизит `ВидДействия`. Встроенных видов четыре.

| Вид | Что происходит |
|-----|----------------|
| `ТолькоПоказать` | Ничего. Значения показаны, кнопка действия скрыта. |
| `ЗаполнитьФорму` | Отмеченные значения переносятся в **открытую форму** объекта. Объект не записывается: форма становится измененной, записывает ее человек. |
| `ЗаписатьОбъект` | Значения записываются в объект в транзакции с блокировкой. |
| `ПользовательскоеДействие` | Вызывается `AI_ДействияПереопределяемый` — все, чего подсистема знать не может. |
| `ВнешнийОбработчик` | Выполняется внешняя обработка из реестра БСП — новое поведение без обновления конфигурации. |

Общая часть у всех видов — **план**: что и в какой реквизит ложится. План
строит `AI_ПрименениеРекомендаций` по карте извлечения, и карта перечитывается
на сервере заново, поэтому пути, пришедшие с клиента, ни на что не влияют.

Контур безопасности одинаков для всех видов:

- белый список — карта извлечения: применить можно только реквизиты,
  перечисленные в ее полях;
- вид действия по умолчанию — `ТолькоПоказать`: пока действие не настроено,
  применить результат нельзя;
- тип значения проверяется по метаданным реквизита;
- доступ к агенту сценария проверяется повторно;
- привилегированный режим не включается — все идет под правами пользователя;
- пользователь отмечает строки и подтверждает действие, причем текст вопроса
  прямо говорит, будет объект записан или нет;
- каждое применение попадает в журнал регистрации под событием
  `AI.ПрименениеРекомендаций`.

Путь через точку не поддержан: в нем нет однозначной строки. Такой путь
отклоняется явным сообщением, а не игнорируется — для табличной части есть
отдельный реквизит карты, см. ниже.

### Табличные части

Строк в документе заранее неизвестно сколько, поэтому плоская схема их выразить
не может. У поля карты есть реквизит `ТабличнаяЧасть`: если он заполнен,
`ПутьРеквизита` означает не реквизит шапки, а **колонку** этой табличной части.

Поля с одним и тем же именем табличной части собираются в схеме ответа в один
массив объектов под ключом, равным имени табличной части. Отдельного имени в
карте нет намеренно: иначе настройщику пришлось бы держать в голове два разных
названия одного и того же.

```
Поля карты                                Схема ответа
key=party_role  ТЧ=Стороны  → Наименование
key=party_org   ТЧ=Стороны  → Сторона        "Стороны": {"type": "array",
key=party_signer ТЧ=Стороны → Подписал         "items": {"type": "object",
key=subject                 → доп. реквизит      "properties": {party_role, …}}}
```

Разбор раскладывает массив в плоские строки с номером: `Стороны [1]: Роль
стороны`, `Стороны [2]: Роль стороны`. Номер строки — то, что связывает поля
одной строки между собой при применении; по нему же собираются строки объекта.
Если модель не вернула массив, появляется одна строка-объяснение на всю
табличную часть, а не по отказу на каждое поле.

Человек отмечает строки по отдельности: можно принять одну сторону и отклонить
другую.

По умолчанию строки **дописываются** к существующим: молча стереть то, что
человек уже внес, хуже, чем добавить лишнюю строку. Заголовочный флаг карты
`ЗаменятьСтрокиТабличныхЧастей` меняет это на очистку — один раз на табличную
часть за применение, а не перед каждой строкой.

Работает и в `ЗаполнитьФорму`, и в `ЗаписатьОбъект`: в первом случае строки
добавляются в форму объекта, во втором — в сам объект, с той же сверкой после
записи.

### Дополнительные реквизиты

Дополнительный реквизит БСП адресуется **наименованием свойства**, а не ссылкой:
план видов характеристик — объект прикладной конфигурации, и ссылаться на него
из расширения означало бы привязать подсистему к одной конфигурации. Поэтому у
поля карты есть реквизит `ДополнительныйРеквизит` — туда пишется наименование
свойства, как оно заведено в базе.

Вид характеристик определяется по типу колонки `Свойство` табличной части
`ДополнительныеРеквизиты` самого объекта, а свойство ищется по наименованию.
Дополнительные сведения в кандидаты не попадают: они хранятся в регистре, а
не в объекте.

**Одноименные свойства.** В живой базе одно имя нередко носят свойства разных
наборов — например, «Суд» у входящей и у исходящей претензии. Пока свойство с
таким именем одно, наборы не проверяются. Если их несколько, выбирается то,
что входит в наборы самого объекта.

Какие наборы у объекта, в БСП решает код конфигурации, а ядро общие модули БСП
не вызывает. Поэтому наборы восстанавливаются по данным — так, как их заводит
сама БСП:

- набор вида: реквизит объекта ссылается на вид, у вида свой набор
  (`ВидДокумента.НаборСвойств` в Документообороте, `ВидНоменклатуры` в
  Управлении торговлей);
- предопределенные наборы объекта: `Справочник_ВнутренниеДокументы` и наборы с
  этим префиксом, например `Справочник_ВнутренниеДокументы_Общие`. Старые
  версии БСП задают их предопределенными элементами, БСП 3 — реквизитом
  `ИмяПредопределенногоНабора`; смотрятся оба места.

Группы наборов не в счет: на форму объекта свойства попадают только из
наборов-элементов. Разбор тоже получает контекст объекта и выбирает свойство
так же, а без контекста окончательный выбор делает применение.

**Свойства-списки.** Значение такого свойства — элемент справочника значений,
подчиненного плану видов характеристик (`ЗначенияСвойствОбъектов` в БСП). В
карте у поля тип «Ссылка», тип ссылки — этот справочник, поиск по
наименованию включен. Значение ищется только среди значений своего свойства
либо свойства, с которым у него общий список (`ВладелецДополнительныхЗначений`):
«Да» есть у многих свойств, и поиск по всему справочнику нашел бы чужое.

Тип у чужого «Да» тот же, поэтому применение сверяет еще и владельца.
Значения приходят в план с клиента, и полагаться на разбор нельзя: чужое
значение заменяется одноименным значением своего свойства, а если такого нет,
строка отклоняется.

**Перечень значений в схеме.** Для поля-списка схема ответа получает `enum` —
наименования значений свойства и пустую строку. Модель выбирает значение, а не
сочиняет: корзину вида «Закупки от 100 до 500 млн руб. (или от 1 до 5 млн
долл.)» по памяти дословно не воспроизвести. Пустая строка оставляет модели
право сказать «в документе этого нет» — иначе строгая схема заставила бы
выбрать хоть что-то.

Перечень — часть строгой схемы: ответ вне него контракт операции отклонит так
же, как ответ не того типа. Поэтому провайдер должен соблюдать схему строго;
Yandex и OpenAI-совместимые API с `json_schema` это делают.

Схема строится без объекта, поэтому у одноименных свойств перечень общий, а
какое из них относится к объекту, решает применение. Списки длиннее 100
значений в схему не попадают и ищутся по наименованию; владелец проверяется и
тогда. Перечень переносится в сценарий вместе со схемой: после изменения
списка значений нажмите «Обновить схему в сценариях» на форме карты.

Отказы говорят прямо, в чем дело:

- у объекта нет табличной части `ДополнительныеРеквизиты`;
- табличная часть устроена иначе — нет колонок `Свойство` и `Значение`;
- свойство с таким наименованием не найдено;
- одноименных свойств несколько, и ни одно не входит в наборы объекта — или,
  наоборот, в наборы объекта входит несколько. Выбирать за настройщика нельзя:
  нужно переименовать или уточнить настройку;
- значения нет в списке своего свойства.

Тип значения проверяется по `ТипЗначения` самого свойства, как и для обычного
реквизита по метаданным.

**В форме объекта** (`ЗаполнитьФорму`) значение ставится в реквизит формы, а не
только в табличную часть. Форма БСП показывает свойства из своих реквизитов,
перечисленных в `Свойства_ОписаниеДополнительныхРеквизитов`, и при записи
собирает табличную часть заново из них — положенное только в табличную часть
при записи пропало бы, хотя помощник отчитался бы «заполнено». Свойство, которого
нет среди выведенных на форму, попадает в «не принято» с объяснением: записать
его через эту форму нельзя.

**В форме карты** у поля есть колонки «Табличная часть» и «Доп. реквизит
(свойство)», в шапке — флаг «Заменять строки табличных частей». Колонки
подсказывают выбор: табличные части объекта, к которому применима карта, и его
дополнительные реквизиты с наименованием набора — одноименные различает только
набор. Список не ограничивает ввод: объекта может не быть в этой базе, а карта
переносится пакетом.

Проверяется сценариями `tests/ui/tabular-and-props.mjs` и
`tests/ui/list-props.mjs`.

### Как действие называется для человека

«Выполнить действие» не говорит пользователю ничего: он видит кнопку, но не
знает, что нажимает. Поэтому у места запуска есть реквизит `ЗаголовокДействия` —
подпись кнопки для этого конкретного действия: «Создать заявку на расход»,
«Отправить на согласование», «Записать реквизиты договора».

Подпись необязательна. Пустая означает «назови по виду действия», и помощник
подставляет встроенное имя: «Заполнить форму», «Записать в объект», «Выполнить
действие». Для первых двух этого обычно достаточно — механика и есть смысл
действия; для прикладного действия и внешнего обработчика подпись стоит задать.

Заголовок окна помощника тоже называет выбранное действие:
«AI-помощник: Заполнить реквизиты по файлу». Помощник открывается окном поверх
карточки, и через минуту работы уже не видно, с чем именно он работает; возврат
к списку действий возвращает и общий заголовок.

Подпись переносится пакетом сценария вместе с остальной настройкой.

### Несколько объектов: пачка через очередь

Выбрали в списке тридцать договоров — и каждому нужен свой разбор: свой файл,
свой ответ модели, свое решение человека. Один запрос по всей пачке дал бы один
ответ, который не к чему применить построчно. Поэтому массовый режим — это
**по операции на объект**, а не один большой запрос.

Режим задается реквизитом `РежимВыполнения` места запуска:

| Значение | Что происходит |
|----------|----------------|
| пусто или `Очередь` | По операции на каждый объект. Значение по умолчанию |
| `ОднимЗапросом` | Прежнее поведение: один запрос, в контексте перечислены все объекты |

Ставить операции в очередь помощнику не нужно самому: приоритет, аренду,
повторы и восстановление прерванных уже держит `AI_ДиспетчерОпераций`. Опрос
пакета заодно двигает очередь — как и в одиночном режиме, поэтому пачка идет и
там, где регламентное задание не работает.

Помощник показывает страницу пакета: объект и его состояние. Готовую строку
открывают — и дальше работает обычный одиночный путь: те же рекомендации, та же
кнопка действия, та же проверка человеком. Возврат ведет обратно к пакету.

Правила, без которых массовый режим врет:

- **уточнение с источником данных разрешается по каждому объекту** своим
  отбором: спрашивать про файл тридцать раз бессмысленно. Уточнение без
  источника задать нечем — один ответ на всю пачку означал бы, что человек
  отвечает за объекты, которых не видел. Такое действие честно отклоняется
  с объяснением, а не выполняется наполовину;
- **отборы контекста проверяются по каждому объекту.** У пачки объекта в
  контексте нет — ключ источника пуст, — поэтому действие предлагается, если
  подходит хотя бы один объект, а неподходящие отсеиваются при запуске, каждый
  со своей причиной в строке пакета;
- **ошибка по одному объекту не отменяет остальные.** Недоступный файл у одного
  договора из тридцати портит одну строку, а не весь пакет.

Ограничение: `ЗаполнитьФорму` в пачке не работает — формы объектов не открыты,
заполнять нечего. Для массовой обработки выбирайте запись объекта, прикладное
действие или внешний обработчик.

Проверяется сценарием `tests/ui/batch-queue.mjs`.

### Заполнение формы

Форма объекта достается помощнику от БСП: при виде `ЗаполнениеОбъекта`
платформа открывает форму обработки, передавая форму объекта владельцем
(`ПолучитьФорму(..., Форма)`). Помощник пробрасывает владельца дальше и
обращается к `ВладелецФормы.Объект`. Свой адаптер может открывать помощника
так же — `AI_ИнтерфейсныеСценарииКлиент.ОткрытьПомощник(..., ЭтаФорма)`.
С владельцем помощник открывается окном поверх вызвавшей формы, без владельца —
обычным окном раздела.

Если помощник открыт не из формы объекта, кнопка заполнения не показывается:
переносить значения некуда.

Форма объекта вправе не принять значение — реквизит может отсутствовать на
конкретной форме, даже если он есть у метаданных. Такие реквизиты попадают в
«не принято» с текстом отказа, а не выдаются за заполненные.

### Запись объекта

После `Записать()` ядро перечитывает записанные реквизиты и сверяет их с тем,
что отправляло. Прикладная логика конфигурации вправе переопределить значение:
в Документообороте, например, `ВнутренниеДокументы.Контрагент` вычисляется из
состава сторон и сбрасывается при любой записи — то же самое происходит и при
обычной записи объектом, без подсистемы. Такие реквизиты попадают в
«отклонено» с причиной, а не выдаются за записанные.

Учтите: запись из ядра выполняется под правами пользователя, но минует форму,
а значит и те проверки, которые живут в модуле формы. Если для объекта важна
логика формы, используйте `ЗаполнитьФорму`.

### Ожидание модели

Обращение к модели идет фоновой агентской операцией, интерфейс при этом не
блокируется: форма опрашивает операцию обработчиком ожидания. Чтобы долгий
ответ не выглядел зависанием, на странице результата на время ожидания
показывается анимированный индикатор (`CommonPicture.AI_ИндикаторОжидания` —
своя картинка, потому что на библиотеку картинок конкретной конфигурации
расширение опираться не может), а в строке состояния — текущий этап операции
и время ожидания. По завершении индикатор скрывается.

### Внешний обработчик

`ВнешнийОбработчик` — то же прикладное действие, но кодом внешней обработки,
то есть новое поведение без обновления конфигурации.

Реестром владеет БСП: там права, версии, безопасный режим и администрирование.
Исполнение идет платформенными `ВнешниеОбработки.Подключить` / `Создать`,
поэтому ядро не заимствует объекты БСП и не вызывает его общие модули — и то
и другое сделало бы расширение незапускаемым в конфигурациях без БСП. Реестр
читается запросом; текст запроса это данные, а не код, так что в конфигурации
без подсистемы дополнительных обработок действие просто дает внятный отказ.

Подключенная обработка кэшируется на время серверного вызова: многошаговое
действие и проверки иначе подключали бы один и тот же файл заново.

**Имя метода настраивается.** На месте запуска есть `МетодДействия` и
`МетодПроверки`; пусто — берется `ВыполнитьДействие`. Перечислить экспортные
методы обработки платформа не позволяет: метаданные не хранят состав модуля,
рефлексии над BSL нет. Поэтому список для выбора дает сама обработка —
необязательной функцией `СведенияОДействияхLLM()` с таблицей «метод,
представление, назначение, описание, параметры». Нет функции — остаются
стандартные имена и ручной ввод.

Вызвать метод по имени из переменной в BSL иначе нельзя: `Объект[Имя]` — это
свойство, а не метод. Поэтому в ядре есть ровно один `Выполнить`, и в него
попадает не код, а идентификатор: имя метода до подстановки проверяется по
строгому шаблону (буквы, цифры, подчеркивание, до 64 символов, не с цифры).

**Параметры задаются содержимым структуры, а не сигнатурой.** Собрать
произвольный список аргументов в BSL нельзя без генерации кода, поэтому
сигнатура одна — `Метод(Параметры)`. Ядро кладет туда свое, администратор
добавляет свое табличной частью `ПараметрыДействия` (имя, тип, значение);
они приходят обработчику как `Параметры.Дополнительные`, уже приведенные к
объявленным типам.

### Многошаговые действия

Обработчик выполняется на сервере и спросить ничего не может, а в веб-клиенте
модальных диалогов нет вовсе — «спросил и продолжил внутри одного вызова»
невозможно в принципе. Поэтому действие устроено как конечный автомат:
обработчик вместо завершения возвращает `Продолжение` — что спросить дальше, —
мастер это показывает, получает ответ и зовет обработчик снова со следующим
шагом, прежним состоянием и ответом пользователя.

Словарь продолжений тот же, что у декларативных уточнений, поэтому новых
страниц мастера не требуется: `Вопрос` (показывается диалогом),
`ВыборИзВариантов`, `ВводСтроки`, `ВводЧисла`, `ВводДаты`, `Флаг`.

Что стоит помнить:

- это **не одна транзакция**. Записали на шаге 1, спросили, записали на
  шаге 3 — три разные транзакции, и пользователь может уйти посередине.
  Обработчик обязан быть идемпотентным по шагам;
- состояние между шагами переносится через клиент, поэтому оно должно
  переноситься между клиентом и сервером: структуры, массивы, ссылки,
  примитивы — да, произвольные объекты — нет;
- число шагов ограничено сверху, чтобы кривой обработчик не зациклил
  пользователя;
- если словаря не хватает, обработчику остается открыть свою форму и
  дальше вести диалог самому. Богаче словарь не делаем: это был бы
  самодельный UI-DSL.

### Ожидание записи объекта

Связать документ с объектом, которого еще нет в базе, нельзя: ссылка появляется
только при записи. У нового объекта ее нет вовсе, а выданная авансом
(`ПолучитьСсылкуНового`) оставит висящую связь, если человек закроет карточку
без записи. Поэтому многошаговое действие вправе попросить дождаться записи:

```bsl
Параметры.Продолжение = Новый Структура(
    "ВидУточнения,Представление,Подсказка",
    "ОжиданиеЗаписи", "Запись объекта",
    "Запишите документ — после записи создам заявку.");
```

Ядро передает такой шаг помощнику, помощник переходит в ожидание и показывает
подсказку обработчика. Признак записи — заполненная ссылка при
немодифицированной форме; оповещение «Запись_*» для этого не годится, его шлет
прикладная форма по соглашению конфигурации, а механизм обязан работать в
любой. Уже записанный и неизмененный объект проходит проверку сразу: ждать
нечего, ссылка есть.

После записи ядро получает контекст с настоящей ссылкой, и следующий шаг
обработчика видит объект обычным `ПолучитьОбъектПоКонтексту`.

**Записывает по-прежнему человек.** Помощник открыт окном поверх карточки и
блокирует ее, а отпустить окно на ходу платформа не дает: присваивание
`РежимОткрытияОкна` открытой форме проходит без ошибки, но поверх карточки
остается перехватывающий слой, и до кнопки «Записать» не дотянуться. Поэтому на
время ожидания помощник показывает свою кнопку «Записать объект», а нажатие
вызывает `Записать()` у формы объекта — со всеми проверками ее модуля. Прямой
записи объекта в обход формы здесь нет.

Ожидание прекращается само: закрыли карточку — действие не продолжено, прошло
15 минут — остановлено. В обоих случаях помощник говорит об этом прямо, а не
молчит.

Проверяется сценарием `tests/ui/wait-for-write.mjs` — он ходит в живую базу и
обращается к модели дважды, поэтому в обычный прогон UI-смоука не входит.

### Цепочка: одно действие ведет к другому

Разобрали реквизиты дополнительного соглашения, проверка сверила их с основным
договором — и выяснилось, что соглашение относится к другому договору. Дальше
нужен другой сценарий, по другому объекту.

Обработчик такое продолжение **предлагает**, а не запускает:

```bsl
Параметры.СледующееДействие = Новый Структура("МестоЗапуска,Причина",
    "Разобрать основной договор",
    "Реквизиты относятся к другому основному документу.");
```

`МестоЗапуска` — наименование либо ссылка. Ядро проверяет предложение теми же
правилами, что и обычный выбор действия: место должно существовать, быть
активным и доступным пользователю по агенту. Непрошедшее предложение не
молчит — причина уходит пользователю сообщением.

Решает человек: помощник показывает причину и спрашивает, продолжать ли.
Запускать следующий сценарий молча нельзя — он тратит токены и трогает другой
объект.

Ограничители обязательны, потому что предложение приходит от прикладного кода,
а расплачивается за его ошибку пользователь:

- **глубина цепочки — пять звеньев**, дальше помощник останавливается;
- **возврат к уже выполненному действию** обрывает цепочку: это петля;
- **действие, предложившее само себя**, отклоняется ядром сразу;
- **доступ проверяется на каждом звене**, поэтому цепочка не может стать
  способом дотянуться до действия, которое пользователю не разрешено.

Безголовая цепочка возможна и без помощника: у операции есть контракт доставки
результата (`AI_КонтрактыОпераций.ДоставитьРезультат` →
`AI_ОбработчикиРезультатовПереопределяемый.ОбработатьРезультат`), и прикладной
код вправе поставить оттуда следующую операцию сам.

Проверяется сценарием `tests/ui/action-chain.mjs`.

### Проверки кодом

Декларативные `ОтборыКонтекста` — дешевый путь для простых условий. Для
сложных есть `AI_ПрименениеРекомендаций.ПроверитьДоступность` с тремя этапами:
`ВыборДействия` (при сборке списка действий), `ПередШагом`, `ПередДействием`.
Один метод обслуживает все точки: этап приходит в параметрах.

Сначала спрашивается конфигурация (`AI_ДействияПереопределяемый`), потом
внешняя обработка — запрет, объявленный в конфигурации, внешней настройкой не
снимается. Упавшая или медленная проверка не ломает помощника: она трактуется
как отказ, а причина уходит в журнал.

### Прикладное действие

`ПользовательскоеДействие` — точка расширения для всего остального: создать
связанный документ, стартовать бизнес-процесс, отправить на согласование,
записать в свой регистр. Ядро отдает обработчику ключ действия из места
запуска (`КлючДействия`), место запуска, контекст и готовый план, а дальше
решает конфигурация. Если обработчик не установил `Обработано = Истина`,
пользователь получает внятный отказ с именем модуля, а не молчание.

Сигнатура и пример — в `AI_ДействияПереопределяемый.ПриВыполненииДействия`.

## Перенос сценария между базами

Настроенный сценарий живет в данных, а не в коде: место запуска, карта
извлечения, уточнения, отборы и параметры действия — это справочники. Поэтому
перенести его в другую базу можно пакетом, не обновляя конфигурацию.

Пакет — zip: `manifest.json` с описанием настройки и файлы внешних обработок,
которые в ней участвуют. Ссылок на объекты чужой базы в манифесте нет: связи
выражены именами и полными именами метаданных, иначе пакет был бы переносим
только между копиями одной базы.

```bsl
Пакет = AI_ПакетыСценариев.Выгрузить(МестоЗапуска);   // Данные, Имя, Состав
Итог  = AI_ПакетыСценариев.Загрузить(ДвоичныеДанные); // Загружено, Предупреждения, Ошибки
```

В мастере это кнопки «Выгрузить пакет» и «Загрузить пакет» на странице выбора
действия. Видны они только администратору, и право проверяется на сервере, а не
видимостью кнопки.

### Чего в пакете нет намеренно

- **провайдеров, ключей и моделей** — это среда и секреты;
- **агента и профилей доступа** — это права, их выдает администратор базы;
- **прикладных данных** — пакет описывает настройку, а не документы.

Сценарий переносится по имени: его настройки в манифесте есть, но привязку к
агенту и модели делает принимающая сторона. Если сценария с таким именем в базе
нет, загрузка скажет об этом прямо, а место запуска останется без сценария —
вместо тихо неработающей настройки.

### Что делает загрузка

- **проверяет метаданные до единой записи.** Нет объекта, на который настроено
  место запуска, — пакет отклоняется целиком: половина сценария выглядит
  работающей, но ведет себя иначе. Отсутствующий реквизит в карте — это
  предупреждение, поле останется нерабочим;
- **сверяет контрольную сумму** каждой обработки: файл, измененный после сборки
  пакета, не принимается;
- **включает найденную регистрацию обработки, но не создает новую.** Вид,
  публикация, назначение и команды — контракт БСП, и заполнять его за
  администратора означало бы подключить чужой код без проверки. Файл в пакете
  есть, регистрация — работа человека;
- **приносит места запуска выключенными.** Включает их администратор, посмотрев,
  что именно он включает.

Загрузка меняет поведение системы данными: новый промт модели плюс новый белый
список реквизитов, которые разрешено писать. По последствиям это ближе к
установке расширения, чем к вводу справочника, поэтому право административное, а
каждая выгрузка и загрузка попадает в журнал регистрации под событием
`AI.ПакетыСценариев.*`.

## Инструкция для пользователя

Пошаговую инструкцию «куда нажимать» — со снимками экрана, стрелкой и курсором
мыши — собирает отдельный этап сборки `tools\Build-UserGuide.ps1`: он
прокликивает сценарий в веб-клиенте живой базы. Сценарий для этого мастера
лежит в `tests\ui\guides\contract-fill.mjs`.

Подробности: [Инструкции для пользователей](user-guides.md).

## Инструкция по настройке

Отдельно от пользовательской инструкции механизм умеет описывать сам себя:
`AI_Инструкции.СформироватьHTML()` собирает
документ из справочников — какие действия настроены, где они доступны, о чем
помощник спросит, что сделает с результатом, какие реквизиты извлекает карта,
каким обработчиком и методом выполняется действие и с какими параметрами.
Инструкция поэтому не расходится с системой: что настроено — то и написано.

В мастере это команда «Сохранить инструкцию (HTML)» в дополнительном подменю.
Файл самодостаточный: стили внутри, внешних ссылок нет, открывается где угодно
и переживает пересылку почтой. Выключенные места запуска по умолчанию не
показываются — параметр `ТолькоАктивные`.

Данные всегда экранируются: наименование сценария вполне может содержать
кавычки или угловые скобки.

## Безопасность и ограничения

- место запуска не предоставляет дополнительных прав к агенту;
- доступ к агенту повторно проверяется на сервере перед открытием диалога;
- JSON-контекст является описанием источника для модели, а не командой записи
  данных;
- история, сценарий и идентификаторы источника сохраняются в заголовке беседы;
- универсальная обработка не знает семантику вложений и версий файлов
  конкретной конфигурации: таблица с реквизитами объекта описывается картой
  извлечения, а не кодом;
- файл уходит модели тем же конвейером, что и вложение обычного диалога, а чем
  его читать — настройка `СпособРазбораВложений` у провайдера и у сценария.
  При `Авто` у Yandex все, кроме текста, уходит через Files API: Yandex сам
  извлекает содержимое — PDF, сканы, картинки, Office — и отдает модели текст,
  поэтому разбирать может любая модель Yandex, мультимодальная не нужна. Роль
  на Vision требуется только способу «OCR». Подробности, ограничения и проверка
  доставки файла — в [обзоре решения](solution-overview.md#вложения);
- точное размещение команды в панели вложений или документа реализуется
  адаптером целевой конфигурации, но использует тот же публичный API.

Для чувствительных сценариев начальный запрос должен требовать подтверждения
пользователя до любого прикладного действия.

Доступ агента к данным по-прежнему только на чтение: инструменты модели читают
метаданные и выполняют запросы, но сами ничего не меняют. Изменение появляется
лишь как отдельный шаг после показа рекомендаций — его инициирует пользователь,
а не модель, выполняется он в границах карты извлечения и ровно тем способом,
который администратор объявил видом действия.
