# Блокировки и транзакции

**Когда читать:** при проектировании проведения и многодокументных операций, при
разборе конфликта блокировок и взаимоблокировки, при доработке существующего
транзакционного пути.

Большинство производственных инцидентов с блокировками возникает из смешения двух
режимов блокировки, из непреднамеренно открытой транзакции и из удержания
блокировки на время ожидания пользователя.

## Режим управления блокировкой

Свойство конфигурации «Режим управления блокировкой данных» — **`Управляемый`** для
всей конфигурации:

- смешанный режим скрывает дефекты: код, написанный под автоматические
  блокировки, неожиданно конфликтует, когда до того же пути данных доходят в
  управляемом режиме;
- только в управляемом режиме гранулярность блокировки в руках разработчика;
- современные подсистемы БСП исходят из управляемого режима.

Перевод существующего проекта с автоматического режима — отдельная многошаговая
задача, не часть текущей правки.

## Границы транзакции

### Неявные транзакции

Платформа открывает собственную транзакцию вокруг:

- `Записать()` объекта — включая `ПередЗаписью` → запись → `ПриЗаписи` →
  `ОбработкаПроведения`;
- `Удалить()` объекта;
- `НаборЗаписей.Записать()` для набора записей регистра;
- материализации движений в конце `ОбработкаПроведения`.

**Внутри `ПередЗаписью`, `ПриЗаписи`, `ОбработкаПроведения` свою
`НачалоТранзакции` не открывать.** Транзакция уже есть; вложенный вызов
изображает точку сохранения, но отменяет корректный откат по внешней ошибке.
Симптомы — «Транзакция не активна» при откате и частично записанные данные.

### Явная транзакция в вызывающем коде

Когда нужно атомарно записать несколько объектов или объединить запись с правкой
регистров, транзакция открывается в вызывающем коде:

```bsl
НачалоТранзакции();

Попытка

	Документ.Записать(РежимЗаписиДокумента.Проведение);
	// ... остальные изменения ...

	ЗафиксироватьТранзакцию();

Исключение

	ОтменитьТранзакцию();

	ДанныеОшибки = Новый Структура;
	ДанныеОшибки.Вставить("Документ", Документ.Ссылка);
	ДанныеОшибки.Вставить("Подробно", ПодробноеПредставлениеОшибки(ИнформацияОбОшибке()));

	ЗаписьЖурналаРегистрации(
		"Проведение." + Документ.Метаданные().Имя + ".Ошибка",
		УровеньЖурналаРегистрации.Ошибка,
		Документ.Метаданные(),
		Документ.Ссылка,
		НСтр("ru = 'Не удалось провести документ.'"),
		ДанныеОшибки);

	ВызватьИсключение;

КонецПопытки;
```

Форма выше — **единственная** правильная. Отсутствие `Попытка`, отсутствие
`ОтменитьТранзакцию` в ветке исключения, отсутствие повторного возбуждения —
дефект в каждом случае. Диагностировать, а не проглатывать: записать в журнал и
`ВызватьИсключение`. Структурированные данные события и имя события — по
[logging.md](logging.md); контекст ошибки одной склеенной строкой не пишется.

### Внутри транзакции запрещено

- **Диалоги с пользователем.** Любое ожидание ввода держит блокировки живыми и
  останавливает другие сеансы.
- **Длительные операции**, сетевые вызовы, внешние компоненты.
- **Запись в журнал с выводом пользователю** в клиентском контексте: сообщение
  уходит в интерфейс, заблокированный этой же транзакцией.

## Управляемые блокировки

```bsl
Блокировка = Новый БлокировкаДанных;

ЭлементБлокировки = Блокировка.Добавить("РегистрНакопления.ТоварыНаСкладах");
ЭлементБлокировки.Режим = РежимБлокировкиДанных.Исключительный;
ЭлементБлокировки.ИсточникДанных = Товары;
ЭлементБлокировки.ИспользоватьИзИсточникаДанных("Номенклатура", "Номенклатура");
ЭлементБлокировки.ИспользоватьИзИсточникаДанных("Склад", "Склад");

Блокировка.Заблокировать();
```

- **Блокировать до чтения**, затем читать, затем писать. Чтение без блокировки с
  последующей записью оставляет незащищённый промежуток, в котором параллельное
  проведение запишет несогласованные остатки.
- **Блокировать регистр, а не документ.** Блокировка документа регистр не
  защищает: следующее проведение всё равно прочитает устаревшие остатки.
- **`ИсточникДанных`**, а не перебор строк вручную: платформа собирает один
  эффективный запрос блокировки.
- **Блокировка живёт до конца транзакции.** Снять её раньше нельзя, можно только
  завершить транзакцию.

### Режимы

| Режим | Для чего |
|---|---|
| `Исключительный` | путь «прочитал, изменил, записал»: проведение, массовая запись, перерасчёты. Блокирует и читателей, и писателей |
| `Разделяемый` | чтение, которое должно остаться согласованным внутри одной транзакции: отчёт, читающий несколько регистров одним снимком |

По умолчанию для любого пути записи — `Исключительный`. `Разделяемый` применять
осознанно: он не защищает от параллельных писателей, он лишь не даёт им поднять
блокировку до исключительной, пока идёт чтение.

## Порядок блокировок — контракт против взаимоблокировок

Взаимоблокировка требует двух транзакций, берущих блокировки в разном порядке.
Лечится не повторами, а **фиксацией порядка блокировок на весь проект**.

Канонический порядок блокируемых таблиц задаёт проект в
`docs/rules/project/locks.md`. Нейтральный комплект его задать не может: список
таблиц зависит от конфигурации. Пример формы записи:

```
1. РегистрНакопления.ТоварыНаСкладах
2. РегистрНакопления.ТоварыКПередаче
3. РегистрСведений.ЦеныНоменклатуры
4. РегистрНакопления.ВзаиморасчетыСКонтрагентами
```

- Любое проведение, затрагивающее больше одного регистра из списка, блокирует их в
  указанном порядке. Исключений нет.
- Новые регистры **дописываются в конец**, не вставляются в середину:
  перенумерация обесценивает все прошлые ревью.
- Операции «документ проводит документ» наследуют тот же порядок: вызывающий код
  берёт блокировки в каноническом порядке и только потом вызывает подчинённую
  операцию.

Если взаимоблокировка наблюдается под нагрузкой, вопрос не «как сделать повтор», а
«какая транзакция взяла блокировки не в том порядке». Повтор — не исправление, а
маскировка: он превращает отказ в замедление и переносит разбор на потом.

## Шаблоны

### Проведение документа по нескольким регистрам

```bsl
Процедура ОбработкаПроведения(Отказ, РежимПроведения)

	// 1. Объект блокировки собирается один раз, в каноническом порядке.
	Блокировка = Новый БлокировкаДанных;

	БлокТовары = Блокировка.Добавить("РегистрНакопления.ТоварыНаСкладах");
	БлокТовары.Режим = РежимБлокировкиДанных.Исключительный;
	БлокТовары.ИсточникДанных = Товары;
	БлокТовары.ИспользоватьИзИсточникаДанных("Номенклатура", "Номенклатура");
	БлокТовары.ИспользоватьИзИсточникаДанных("Склад", "Склад");

	БлокВзаиморасчеты = Блокировка.Добавить("РегистрНакопления.ВзаиморасчетыСКонтрагентами");
	БлокВзаиморасчеты.Режим = РежимБлокировкиДанных.Исключительный;
	БлокВзаиморасчеты.УстановитьЗначение("Контрагент", Контрагент);

	Блокировка.Заблокировать();

	// 2. Прочитать остатки и проверить условия проведения.
	// 3. Записать движения через Движения.X.Добавить, Записывать = Истина.

КонецПроцедуры
```

### Массовая операция по многим документам

Если атомарность нужна по всему набору — транзакция у вызывающего кода. Если нет —
транзакция на документ, с продолжением после отказа и записью каждого отказа в
журнал. Выбор определяется бизнес-требованием, а не удобством кода.

Одну транзакцию на тысячи документов не держать: эскалация блокировок и давление
на журнал останавливают кластер.

### Обновление статуса вне проведения

```bsl
НачалоТранзакции();

Попытка

	НаборЗаписей = РегистрыСведений.СтатусыИнтеграции.СоздатьНаборЗаписей();
	НаборЗаписей.Отбор.Заказ.Установить(СсылкаЗаказа);
	НаборЗаписей.Заблокировать();
	НаборЗаписей.Прочитать();

	// ... изменение набора ...

	НаборЗаписей.Записать();
	ЗафиксироватьТранзакцию();

Исключение
	ОтменитьТранзакцию();
	ВызватьИсключение;
КонецПопытки;
```

`НаборЗаписей.Заблокировать()` — краткая форма управляемой блокировки по отбору
набора. Применять, когда смысл операции ровно в том, чтобы эти записи перезаписать.

## Диагностика

### Симптомы

- «Конфликт блокировок при выполнении транзакции» — другая транзакция держит тот
  же ключ в несовместимом режиме дольше таймаута ожидания.
- «Deadlock» — две транзакции ждут друг друга; причина в нарушенном порядке
  блокировок.
- Отказ получения записи регистра при проведении — обычно конфликт на самом
  регистре, а не на наборе записей.

### Инструменты

- **Технологический журнал** (`logcfg.xml`), события `TLOCK` и `TDEADLOCK` по
  проблемному регистру. Это единственный достоверный источник ответа на вопрос
  «какие именно две транзакции столкнулись».
- **`ТранзакцияАктивна()`** — только для самопроверки внутри кода, не для
  межсеансовой диагностики.
- **Представления СУБД** (для серверной базы) — живой снимок ожиданий.
- **Повторное проведение под отладчиком** — чтобы увидеть фактическую
  последовательность вызовов блокировки.

Разбор вести в порядке из [debugging.md](debugging.md): воспроизвести, выдвинуть
гипотезы, поставить эксперимент, потом править. Блокировки особенно плохо
поддаются угадыванию: правка «на всякий случай» здесь обычно добавляет второй
дефект, не убирая первый.
